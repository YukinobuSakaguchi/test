## 0. 読み方と最優先ルール

この文書の「§2 データ取り扱いルール」は、他のすべての記述より優先する。
実装・テスト・デバッグのどの場面でも、**実データ(給与明細、銀行・カードの明細、レシート、診療領収書、投資Excel)を、本人の明示許可なくClaude Codeに読ませない**。

## 1. 目的・スコープ

### 1.1 目的
本人専用の家計管理アプリ。給与明細・銀行・カード・レシート等を取り込み、自動で分類・可視化し、将来的にライフプランと固定費削減までを一つのデータで扱う。

### 1.2 優先順(本人指定)
1. **見える化**(収支・純資産・納期の可視化)
2. **ライフプラン**(養育費・住宅・退職など)
3. **サブスク・固定費の削減、診断**

### 1.3 スコープ外(当面)
- 金融機関への自動ログイン・API連携による明細自動取得(外部にID・資格情報を渡すため)
- 複数ユーザー対応、クラウド同期
- 税務・法規の最終判断(医療費控除の可否など。集計材料の提示までで、判断は本人)
- 投資の売買判断(本人に残す)

### 1.4 実行環境
- Windows PC 1台(CPUのみ、GPUなし)
- ローカル完結。**スマホからの閲覧は将来拡張**(§5.3)として設計に織り込む

## 2. データ取り扱いルール(最優先)

### 2.1 AI利用の許可範囲(本人決定)
- **原則ローカル処理。**
- 外部AI(OCR・画像認識・LLM)は、**個人情報を伏せた状態であれば送信可**。
- 伏せ字化の対象: **氏名、カード番号、口座情報、住所、電話番号、社員番号、勤務先名**(加えて、メールアドレス、郵便番号、銀行摘要中の振込相手の個人名)。
- 外部送信は**既定でオフ**。文書ごとに本人が許可し、送信内容(伏せ字化後)をプレビューで確認できること。送信履歴(日時・文書ID・送信先・伏せ字化後のハッシュ)をローカルに記録すること。
- 伏せ字化後の再検査(§10.4)に失敗した場合は**送信禁止**。

### 2.2 開発中の実データの扱い
| データ | 方針 |
|---|---|
| 給与明細(画像) | Claude Codeに**読ませない**。架空データ(§12)で開発し、実物の検証は本人のPC上でアプリを動かして、結果から個人情報を除いてフィードバックする |
| 銀行・カードCSV | 同上。形式(列名・文字コード・区切り)は、**ヘッダ行と、値をダミーに置換した1〜2行**だけを共有する |
| レシート・診療領収書 | 同上(診療内容は要配慮情報に近い) |
| 投資Excel | 本人は「そのまま渡す」意向。ただし**氏名・口座番号・証券口座番号が含まれる場合は、読ませる前に本人が確認・除去する**。判断は本人 |

本人が「実データを読ませてよい」と明示した場合のみ例外とし、その旨を作業記録に残すこと。

### 2.3 保存・バックアップ
- DBは暗号化(SQLCipher等。選定は実装時)。パスフレーズはコードに書かない。
- 個人データ・DB・設定(`local/`, `data/`, `*.db`, `redaction_profile.json`)は**Git管理外**。リポジトリの `.gitignore` で除外済み。
- リポジトリは、公開・非公開を問わず、**個人データを置かない**(架空データのみ)。
- バックアップは暗号化した1ファイルで取得する。

### 2.4 最終判断の責任境界
分析・整理・草案・突合結果の提示までがアプリの役割。次は本人が決める: 法規・税務の最終解釈、確定申告等の提出、投資の売買、人事・家族に関する判断。

## 5. アーキテクチャ

### 5.1 構成
```
[取込: CSV / 画像 / Excel]
      ↓
[コア(Python)] 取込アダプタ → 正規化 → 重複・振替の突合 → 分類 → 集計・シミュレーション
      ↓
[データ] SQLite(暗号化)  ← 全データの唯一の保管場所
      ↓
[API(ローカル限定バインド)]
      ├─ PC: ブラウザ画面(ダッシュボード、確認待ち画面)
      └─ 将来: スマホ(自宅LAN内、またはVPN経由で閲覧)
```

### 5.2 設計原則
- **コアとUIを分離**する。ビジネスロジックはUIから独立したパッケージにし、UIは後から差し替え可能にする。
- 金融機関・カードごとに**取込アダプタ**を作る(共通インターフェース、§7)。
- 取込の**冪等性**: 同じ明細を二度取り込んでも二重登録しない。
- **証跡は削除しない**。家計の数え方(支出)は証跡から導出する。

### 5.3 スマホ拡張の織り込み
- データをクラウドに置かない。PCのAPIを家庭内ネットワークまたはVPNで参照する形を第一候補とする。
- 初期実装でも、API(読み取り系)はHTTPで公開できる構造にしておく(認証必須、ローカルバインド既定)。
- UIはレスポンシブにしておく(後からスマホで使える余地を残す)。

### 5.4 技術候補(最終選定は実装時)
- 言語: Python。UI: Streamlit(速く作れる)またはFastAPI+軽量Web画面(スマホ対応を重視する場合)。コアとUIが分離されていれば、後から変更できる。
- OCR(ローカル): Windows標準OCR、Tesseract(日本語)、PaddleOCR(CPUで動作可)など。**精度は実サンプルで比較して選定する**(未検証)。
- LLMはローカルでは動かさない前提(GPUなし)。分類・診断はルールと辞書で行う。

## 6. データモデル(概念設計)

「**証跡(Evidence)**」と「**支出(Expense)**」を分けるのが中核。1回の買い物が複数の記録(レシート、カード明細、銀行引落)に残るため、証跡は全部保存し、家計として数える1件を支出として別に持つ。

### 6.1 主要テーブル(カラムは例。実装時に確定)
| テーブル | 役割 | 主なカラム |
|---|---|---|
| `accounts` | 口座・カード・現金・ポイント・ローン等 | id, kind(bank/card/cash/point/loan/invest), name, institution, closing_day, payment_day |
| `documents` | 取り込んだ元ファイル | id, source_kind, file_hash, imported_at, adapter, adapter_version |
| `evidence` | 取引の最小単位の生記録 | id, document_id, account_id, kind(bank_line/card_line/receipt/medical/payslip_line), occurred_on, posted_on, amount, currency, counterparty_raw, memo_raw, raw_json |
| `expenses` | 家計として数える1件 | id, occurred_on(**カード利用日**), amount_total, category_id, merchant, is_medical, confidence, status(auto/confirmed/review) |
| `expense_evidence` | 支出と証跡の紐づけ | expense_id, evidence_id, role(primary/receipt/settlement), match_score, match_rule |
| `expense_funding` | 財源の内訳 | expense_id, source(card/cash/bank/point), account_id, amount |
| `transfers` | 口座間移動・カード精算 | id, from_evidence_id, to_evidence_id, kind(own_account/card_settlement/charge) |
| `categories` / `category_rules` | 費目と分類ルール | pattern, category_id, source(user/learned), priority |
| `review_queue` | 確認待ち | id, kind(ambiguous_match/unmatched/unknown_item/low_confidence), refs, created_at, resolved_at |
| `assets` / `liabilities` | 資産・負債(最小限の台帳) | 種別、残高、評価日。ローン、投資、固定資産 |
| `obligations` | 税・車検・保険等の納期 | kind, due_on, amount, recurring, note |
| `import_log`, `external_send_log` | 取込・外部送信の監査記録 | §2.1 |

### 6.2 不変条件(テストで担保する)
- 同一の `file_hash` や同一の証跡(口座・日付・金額・摘要・行番号が同じ)を二重登録しない。
- カード精算の銀行引落は、支出の合計に**含まれない**(`transfers.kind=card_settlement`)。
- 口座間移動は、収入にも支出にも**含まれない**。
- 支出の `amount_total` = `expense_funding` の合計(ポイントを含む)。
- 証跡は、支出に紐づいていなくても保存されている(確認待ちとして残る)。

## 8. 突合(重複排除)

### 8.1 計上の考え方
- **支出は、カード利用日で計上**する(本人決定)。引落日は `evidence.posted_on` として保持する。
- カード利用の支出に対して、銀行のカード引落は**精算**であり、支出ではない。
- 月次の収支は利用日基準、口座残高の推移・資金繰りは引落日基準で見る。

### 8.2 突合ルール
| ID | 突合 | 条件 | 結果 |
|---|---|---|---|
| R1 | レシート ↔ カード明細 | 金額一致 + 日付が±N日(Nは設定、初期値3)+ 店名の類似 | 同一支出に統合。カード明細が主、レシートは補助 |
| R2 | カード明細 ↔ 銀行引落 | 同一カード・同一引落日の明細合計 = 銀行の引落額 | 銀行行を `card_settlement` とし支出から除外 |
| R3 | 銀行の直接引落(電気・通信等) | 他の証跡に対応なし | その行を支出にする |
| R4 | レシートのみ(現金払い等) | 他に対応なし | レシートを支出にする(財源は現金) |
| R5 | 口座間移動 | 同額・近い日付で出金と入金が対 | `own_account` 振替として収支から除外 |
| R6 | 給与明細 ↔ 銀行入金 | 差引支給額 = 入金額 | 給与収入の裏付けとして紐づけ。二重計上しない |

- **締め日・引落日はカードごとに設定値で持つ**(カード会社の仕様は実物で確認する。NOT VERIFIED)。
- 各突合は**確信度**(0〜1)を持つ。**高確度のみ自動確定**、それ以外は `review_queue` へ。当面は確認待ち中心で運用する。
- 誤ってつなぐより、聞く方を優先する。

### 8.3 レシート
- 画像をOCRし、日付・店名・合計・(可能なら)品目と税額を取る。
- OCR精度が低い場合は、確認画面で手修正。レシートはカード明細との突合で補完できるため、**まずカード明細を正にする**。

### 8.4 診療領収書(病院)
- 領収書(必要なら診療明細)を取り込み、同じ突合ルールで、カード・銀行に紐づける。
- 家計の支出としては、通常の1件。加えて `is_medical` タグと、**受診者・医療機関・金額・日付**を保持し、医療費控除の集計材料にする。
- 控除の可否・金額・申告は、本人の最終判断(アプリは集計材料の提示まで)。

### 8.5 エッジケース(最初から設計に含める)
- 同額・同日・同店の複数取引(曖昧一致 → 確認待ち。テスト用に架空データで再現)
- カードの分割・リボ(1回の購入が複数月の引落に分かれる)
- 返品・取消・返金(マイナスの取引は元の支出に紐づける)
- 電子マネー・プリペイドのチャージ(チャージは移動、利用時が支出)
- ATM引出(現金の使途が不明な間は「現金引出」費目。レシートで補完)
- カード払いとポイントの併用払い
- 同じ明細ファイルの二重取込
- 月をまたぐ利用(利用日基準と引落日基準の差)

### 8.6 ポイント払い
- **ポイント利用分も支出に含める**(本人決定)。
- 支出総額 = 現金・カード払い + ポイント払い。`expense_funding` で財源を区別する。
- ダッシュボードは2つの見方を持つ: **支出総額(ポイント込み)** と **現金流出(ポイント除く)**。後者は口座残高・貯蓄率との整合に使う。
- 付与(還元)ポイントは**当面計上しない**。必要になればポイント残高を資産として追加する(Phase 2以降で検討)。

## 9. 給与明細(画像のみ・書式が変わる)

難易度は中〜高。**確認画面つきの半自動**を前提とする。月1回・数ページなので、確認コストは小さい。

### 9.1 方式
1. 画像を前処理(傾き補正、二値化等)し、**ローカルOCR**で文字と座標を取得する。
2. **位置に依存しない**。項目名の辞書(基本給、各手当、健康保険料、厚生年金、雇用保険、所得税、住民税、差引支給額など)で金額を探す。書式が変わっても、項目名が同じなら読める。
3. 辞書にない項目は「未知の項目」として確認待ちに回し、本人が分類すると辞書に追加される(学習)。
4. **検算**で誤読を検出する。
   - 総支給額 = 支給項目の合計
   - 総控除額 = 控除項目の合計
   - 差引支給額 = 総支給額 − 総控除額
   - 差引支給額 = 銀行の入金額(§8.2 R6)
   - 1つでも合わなければ「要確認」にする。
5. ローカルOCRで読めないものは、(a)手修正、(b)**伏せ字化したうえで外部の画像認識AIに送る**(§2.1の条件を満たす場合のみ)。

### 9.2 注意
- 実物の明細で精度を確認していない。**精度は未検証**。実装後、本人のPC上で検証する。
- 伏せ字化は、画像では**文字の座標を使って該当部分を塗りつぶす**必要がある(§10.3)。氏名・社員番号・勤務先名・住所が写る部分が対象。
- 明細に健康状態などの機微な情報が含まれる場合は外部に送らない。

## 10. 伏せ字化モジュール

### 10.1 目的
外部AIへ送る前に個人情報を除去する安全装置。**外部送信の唯一の出口に必ず通す**(通さない経路を作らない)。

### 10.2 対象(本人決定)
氏名、カード番号、口座情報(口座番号・支店番号)、住所、電話番号、社員番号、勤務先名。追加: メールアドレス、郵便番号、銀行摘要の振込相手(個人名の可能性)。

### 10.3 機能
- **テキスト**: 検出器(§10.4) → プレースホルダに置換(例: `[氏名1]`、同じ値は同じ番号)。
- **CSV**: 名義・口座・カード番号の列は全面マスク、他の列はセル単位で処理。
- **画像**: OCRの座標で該当領域を塗りつぶす。検出はテキストと同じ検出器を使う。
- **置換の対応表(元の値)はローカルにのみ保持**し、外部へ送らない。

### 10.4 検出方式と検証
- **既知の値(プロファイル)**: 本人の氏名・勤務先・住所・電話・口座・社員番号・カード番号を、Git管理外のローカルJSONで持つ。氏名は空白あり/なし/全角空白、姓・名単独の表記ゆれも検出する(1文字の語は誤検出が多いため対象外)。
- **パターン**: カード番号(Luhn検査で誤検出を抑制、マスク形式も検出)、電話、郵便番号、メール、都道府県から始まる住所。
- **ラベル付き**: 「氏名」「社員番号」「口座番号」「勤務先」等の直後の値(ラベルは残し、値だけ置換)。
- **誤検出を避ける**: 金額・日付・店名・「お客様」等は置換しない(分類精度を維持)。
- **再検査(ゲート)**: 伏せ字化後のテキストを再走査し、残存があれば**送信禁止**(例外)。**再検査では、自分が付けたプレースホルダ(`[氏名1]` 等)を検出対象から除外すること**。
  - 備考: 事前の試作で、再検査がプレースホルダ自体を再検出して誤判定する不具合が出た。実装時に、プレースホルダを持つ範囲を除外する、または検出器をプレースホルダの形式と衝突しないようにする。
- 銀行摘要の振込相手の伏せ字化は、分類精度を下げるため**オプション**(外部送信時のみ有効)。

### 10.5 ローカルの既存スキルとの接続
- 本人のローカルに、簡易な伏せ字スキルがある。**部分的に流用してよい**。
- モジュールは追加検出器 `(text) -> Iterable[Finding]` を差し込める構造にする。スキルの検出ロジックはこの形に包んで接続する。
- スキルの内容(正規表現・辞書・手順)を確認してから、流用範囲を決める。**この段階で、スキル自体にも実データを入れない**(スキルの確認は、実データなしで、ファイル内容を見ることから始める)。

### 10.6 受け入れ基準
- 架空データ(§12)のうち個人情報を含む部分が、すべて除去される。
- 金額・日付・店名・費目に影響する語が、置換されない(誤検出の回帰テストを持つ)。
- 再検査が、プレースホルダを誤検出しない。
- 画像の伏せ字化後に、OCRをかけ直しても、対象の文字が読めない。

## 12. 架空データ

目的: 実データを使わずに、取込・突合・伏せ字化・ダッシュボードをテストする。

### 12.1 生成するもの
- 銀行CSV(楽天銀行・三菱UFJ・池田泉州の**想定形式**)、カード明細CSV(楽天VISA、JCB等)。**形式は実物で確認するまで暫定**(§7.2)。
- レシート画像、診療領収書の画像、給与明細の画像(**検算が成立する金額**)。
- 架空の人物情報(氏名・住所・電話・口座・カード番号・社員番号・勤務先)。**カード番号はLuhn検査を通るテスト用の番号**。
- `ground_truth.json`: 期待される突合結果(支出の件数と金額、精算・振替の対応、確認待ちにすべき件)。

### 12.2 必ず含めるシナリオ
1. 同一の買い物が、レシート・カード明細・銀行引落(翌月の一括)の3つに現れる(R1、R2)。
2. 銀行の直接引落(電気・通信)。カードや他の証跡と対応しない(R3)。
3. 現金払いのレシートのみ(R4)。
4. 口座間移動(楽天銀行 ⇔ 三菱UFJ等)(R5)。
5. 給与の入金と、明細画像(差引支給額が一致)(R6)。**書式違いの明細を2種類**(項目の並び・名称が異なる)。
6. ポイント併用払い(カード+ポイント)。
7. 病院の支払い(カード払い+領収書。`is_medical` を付与)。
8. 同額・同日・同店の曖昧一致(確認待ちになること)。
9. 返品・取消。
10. ATM引出。
11. 同じファイルの二重取込。
12. 月またぎのカード利用。
13. 氏名・カード番号・住所などが混在する行(伏せ字化のテスト)と、伏せ字化してはならない店名・金額。

### 12.3 要件
- 乱数は**固定シード**。再生成しても、同じ結果になる。
- 個人情報に見える値は、すべて架空であること(実在の氏名・住所・番号を使わない)。
- 日本語フォントが必要(画像生成時。環境に合わせて指定)。

## 13. フェーズ計画と受け入れ基準

### 13.1 Phase 1: 見える化
**範囲**
- 銀行3行・カードのCSV取込、分類、二重計上除去(§8)
- 給与明細画像の取込(§9。確認画面つき)
- 投資Excelの読み取り(構造確定後)、純資産の推移
- ローン・各種税(固定資産税、自動車税、住民税)・車検の最小限の手入力登録
- ダッシュボード: 月次収支(支出総額・現金流出)、費目別、純資産、納期カレンダー、確認待ち画面
- 伏せ字化モジュールと外部送信ゲート

**受け入れ基準**
- 架空データで、突合結果が `ground_truth.json` と一致する。
- 二重計上が0件。カード引落・口座間移動が収支に含まれない。
- 同じファイルを二度取り込んでも、件数が変わらない。
- 曖昧な取引が確認待ちに入り、自動確定されない。
- 給与明細の検算が失敗した場合に、要確認になる。
- 実データでの精度は、本人のPC上で検証し、個人情報を除いた形でフィードバックする。

### 13.2 Phase 2: ライフプラン
- 前提入力(提案どおり。細部は本人と詰める): 家族構成、収入見込み(昇給率)、**養育費・教育費の期間と額**、住宅(ローン・固定資産税)、車の買い替えと維持費、退職時期、投資の想定利回り。
- 長期の収支・資産推移の試算。複数シナリオ(標準・悲観・繰上返済など)の比較。
- 投資Excel帳票との統合と、帳票の改善。
- 前提値に依存するため、結論ではなく、**前提を変えて見比べる道具**として設計する。

### 13.3 Phase 3: 削減・診断
- サブスクの自動検出(同額・同店・周期)と年額換算、解約候補の提示。

- 車の維持費・総所有コスト。

## 14. Claude Code向け作業ルール

1. **実データを読まない・貼らない**(§2.2)。架空データで開発し、実データの検証は本人のPC上で行う。
2. 個人データ・DB・設定ファイルをGitに入れない。コミット前に `git status` で確認する。
3. 外部送信は、伏せ字化モジュールの再検査ゲートを通った場合だけ。通さない経路を作らない。
4. **検証できていないことを、できたと書かない**。テスト・実行結果は、実際に実行したものだけを報告する。
5. 数値計算(金額・比率)は、式→代入値→結果が追える形でテストにも残す。
6. 変更は、依頼に必要な最小範囲にとどめる。依頼と無関係な大規模リファクタリングをしない。
7. プログラミングが専門でない本人にも追えるよう、変更時に「何を実現する処理か、全体構造、変更箇所と理由、実行方法、確認方法」を添える。
8. 作業環境の既定値はWindows。パス・改行・文字コード(Shift_JIS/UTF-8)に注意する。

## 16. 用語
- **証跡(Evidence)**: 取り込んだ生の記録。レシート、カード明細の1行、銀行の1行など。
- **支出(Expense)**: 家計として数える1件。複数の証跡を紐づける。
- **精算**: カード利用額の銀行からの引落。支出ではない。
- **財源**: 支払いに使った手段(現金、カード、ポイント)。
- **確認待ち**: 自動で確定せず、本人の確認を待つ項目。

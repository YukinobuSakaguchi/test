> この文書はエンジニアリング計画であり、投資助言ではない。売買・実資金投入・自動発注の可否は本人が判断する。

## 0. 結論（先に要点）

1. 記事の骨格「**AIが読む・コードが決める・人が署名する**」は妥当で、そのまま採用する。
2. ただし記事のサンプルコードには、**ペーパーでも検証を歪める欠陥**がある（空売りの暴発、同一銘柄の二重発注、キルスイッチの最大15分遅延、例外・拒否応答の未処理など。§2.3）。そのため、記事のコードはそのまま動かさず、修正した設計で作り直す。
3. 推奨する進め方は、**「リサーチデスク（読む・要約する・ルール違反を検知する）」を先に完成させ、売買機能は後段の判断ゲートに置く**こと。
   - 理由: 記事自身が「AIで儲かるとは限らない」と認めている。長期投資を軸にした使い方なら、リサーチ部分だけで実用価値があり、損失リスクはほぼない。
4. 自動発注は Phase 5 までは行わない。承認モード（提案をファイルに書き出し、本人が承認したものだけを paper 口座で発注）に留める。

- **`stop_reason == "refusal"`**（安全分類器による応答拒否）が返る場合がある。このとき `parsed_output` が使えない前提で、**hold 扱い**にして記録する。
- 構造化出力と citations（引用機能）は併用できない（400）。根拠の追跡は `sources` フィールドで行う設計を維持する。

### 2.3 記事のサンプルコードの欠陥と対処

| # | 症状 | 根因 | 対処（本計画での設計） |
|---|---|---|---|
| A | 保有していない銘柄に `sell` が出ると**空売り**になる。売りの場合、ストップがエントリーより上にあるかの検証もない | `action` の `sell` を「新規売り」と「保有株の決済」の区別なく発注している | 当面は**ロングのみ**とする。`sell` は保有ポジションの決済に限定し、数量は保有株数。空売りはスキーマで受け付けない |
| B | 15分ごとに同じ銘柄で再び buy が出て**ポジションが積み増される** | 銘柄ごとの保有・未約定注文を確認していない（全体の保有数上限しか見ていない） | 銘柄ごとに保有中・未約定・冷却期間中（例: 決済後N日）かを判定し、該当すれば拒否する |
| C | サイジングに使った価格と実際の約定価格がずれ、損失が 1% 上限を超えうる。ギャップダウン時はストップ注文も滑る | 成行注文であることと、ストップは損失を保証しないこと | 指値エントリー（最新価格±許容幅）を基本とし、約定後に実際のリスク額を再計算して記録する。「1%」は**目標値であって保証ではない**と明記する |
| D | キルスイッチが**最大15分遅れて**効く。市場時間外の `close_all_positions` は即時に約定しない | メインループの先頭でしか KILL ファイルを確認していない | 監視を別プロセスに分け、短い周期（例: 30秒）で確認する。発動後は新規処理を止め、残存ポジションと未約定注文を確認して記録する |
| E | API エラー・タイムアウト・応答拒否で**ループが停止するか、例外で落ちる** | 例外処理と再試行がない。`while` の無限ループに依存している | 「1回実行して終わるジョブ」をスケジューラから起動する形に変える（§3.2）。エラーは種類別に扱い、AI側のどの失敗も hold として記録する |
| F | 記録から判断を**再現できない** | ジャーナルに thesis しか残していない | 入力（ニュース本文またはハッシュとURL）、プロンプトのバージョン、ルールのバージョン、トークン使用量、応答の終了理由も記録する |
| G | 隔離タグの ID が 16bit と短く、ニュース本文にタグ文字列が混ざっても除去されない | `token_hex(2)` を使っており、本文の無害化処理がない | `token_hex(8)` に伸ばし、本文中の `pasted_content` に一致する文字列を除去する。根本の防御は、記事どおり「モデルに数量と発注の権限を持たせない」構造そのもの |
| H | high 確度の時だけ執行し、プロンプトでは「high は稀に」と指示しているため、**取引がほぼ発生せず評価できない** | 評価対象を「約定した取引」に限っている | hold を含む**全 thesis の事後的な当否**（invalidation に当たったか、N日後の値動き）を評価対象にする（§5） |
| I | 新しい情報がない銘柄にも毎サイクル Opus を呼び、**コストがかさむ** | 全銘柄を一律に呼んでいる | 前回から新規ニュース・開示・閾値を超える価格変動があった銘柄だけを分析する（差分トリガー） |

## 3. システム構成

### 3.1 役割分担（記事の3層に記録と監視を加える）

```
[データ取得]  価格（Alpaca）/ ニュース / SEC EDGAR開示
     │ 差分検知（新規情報がある銘柄だけ通す）
     ▼
[アナリスト]  claude-opus-5-5（構造化出力 TradeThesis）── 夜間の要約は claude-sonnet-5-5 の Batch API
     │ thesis（推奨のみ）
     ▼
[リスクエンジン]  純Python（rules.yaml の数値で判定・数量決定）← AIは関与しない
     │ 承認/却下 + 数量 + 理由
     ▼
[執行]  Phase 3〜4: pending.csv に書き出し → 本人が承認 → paper 発注（OTO + ストップ）
     ▼
[ジャーナル]  全 thesis・判定・注文・入力・バージョン（JSONL → Excel 向けに CSV 出力）

[キルスイッチ監視]  別プロセス・30秒周期（KILL ファイル、日次損失上限）
```

### 3.2 実行形態

- 無限ループは使わず、**1回実行して終わるジョブ**をスケジューラから起動する。こうするとPCの再起動、スリープ、Windows Update でもプロセスの生死を管理せずに済み、停止は「次の起動をしない」だけで済む。
- 稼働場所の選択肢:

| 選択肢 | 長所 | 短所 | 推奨時期 |
|---|---|---|---|
| 自宅の Windows PC + タスクスケジューラ | 追加費用なし、手元で見られる | スリープ・停電・更新による再起動。米国市場の時間帯は日本の夜間〜早朝 | Phase 1〜4 |
| 小型クラウドVM（Linux + cron） | 常時稼働 | 月額費用、保守、APIキーをクラウドに置くリスク | Phase 5 で常時稼働が必要になった場合 |
| Anthropic Managed Agents の定期実行 | ループやスケジューラの実装が不要 | ベータ機能。ブローカーの認証情報をどこに置くかの設計が必要 | 選択肢として保留 |

### 3.3 ディレクトリ構成（案）

```
trading_desk/
  config/
    rules.yaml          # リスクパラメータ・許可銘柄・ウォッチリスト（git管理し、変更履歴を残す）
    prompts/analyst_v1.md
  src/trading_desk/
    schema.py           # TradeThesis（Pydantic）
    data.py             # 価格・ニュース・開示の取得と差分検知
    sanitize.py         # 外部テキストの隔離タグ付けと無害化
    analyst.py          # Opus 呼び出し（応答拒否・解析失敗は hold）
    overnight.py        # Sonnet Batch による要約と朝ブリーフ
    risk.py             # リスクエンジン（純粋関数）
    executor.py         # pending 出力 / 承認済み注文の paper 発注
    journal.py          # JSONL への記録と CSV 出力
    killswitch.py       # 監視プロセス
    cli.py              # run-intraday / run-overnight / approve / kill / report
  tests/
  var/                  # journal, pending, KILL（git管理しない）
  .env.example          # キーの雛形（実際のキーは .env に置き、git管理しない）
```

## 5. 評価方法（Phase 5）

- **バックテストはしない**（記事どおり）。LLM の判断は学習データ経由で結果を知っている可能性があるため。ただし純コード部分（リスクエンジン、サイジング）は過去データでテストしてよい。
- 評価指標（案）:
  - thesis の当否: buy/sell 推奨のうち、N営業日以内に invalidation 条件に当たった割合と、価格がストップに達した割合
  - hold の妥当性: hold とした銘柄のその後の値動き分布（「見送り」が機会損失だったか）
  - リスクエンジンの却下理由の内訳: 却下が負け筋を除いているのか、勝ち筋を除いているのか
  - 運用指標: ジョブの成功率、応答拒否・解析失敗の率、1日あたりのコスト
  - 比較対象: 同期間のウォッチリスト等金額保有と SPY 保有
- 注意: 8〜12週・5銘柄では統計的に結論を出すには標本が少ない。「破綻しないこと」と「プロセスが記録どおり動くこと」の確認が主目的であり、収益性の証明にはならない。

## 6. コスト試算（仮定値。Phase 2 で実測値に置き換える）

前提（すべて仮定）: ウォッチリスト5銘柄、場中は15分周期で26回/日、1回あたり入力8,000トークン、出力（思考を含む）3,000トークン、effort は medium、月21営業日。

- 1回あたり = 8,000 × $4/1M + 3,000 × $20/1M = $0.032 + $0.060 = **$0.092**
- 全銘柄・全サイクルで呼ぶ場合 = 5 × 26 × $0.092 = **$11.96/日** → × 21日 = **約 $251/月**
- 差分トリガーで1銘柄あたり平均3回/日に絞る場合 = 5 × 3 × $0.092 = **$1.38/日** → × 21日 = **約 $29/月**
- 夜間要約（Sonnet 5.5 Batch: $1 / $5 per MTok）で、1銘柄あたり入力50,000・出力2,000トークンの場合 = 5 × (50,000 × $1/1M + 2,000 × $5/1M) = 5 × ($0.05 + $0.01) = **$0.30/日**

結論: コストを決めるのは**場中の呼び出し回数**である。差分トリガー（§2.3 I）は必須とする。システムプロンプトをプロンプトキャッシュに乗せれば入力単価はさらに下がる（効果は実測で確認する）。

## 7. リスク・反論・代替案

| 観点 | 内容 | 対応 |
|---|---|---|
| **期待値の根拠がない（最も強い反論）** | プロセスが規律的でも、収益の源泉（エッジ）は示されていない。5銘柄の大型株・15分周期では情報優位を得にくい | 売買機能は判断ゲートの後ろに置く。リサーチデスク単体でも価値が出るように作る |
| 投資方針との不一致 | 短期の売買判断と、長期・高配当の投資方針とは目的が異なる | 代替案: 同じ構成で「保有銘柄の決算・開示の要約」「減配・業績悪化の兆候検知」「自分の投資ルールへの違反警告」に使う |
| 運用負荷 | 米国市場の取引時間は日本の夜間〜早朝。アラート対応は家庭生活と衝突しうる | 承認モードは朝にまとめて処理する運用にする。夜間に人手が必要な設計を避ける（ストップ注文はブローカー側に置く） |
| モデルに由来するバイアス | 知識カットオフ後のニュースでも、大型株への一般的な見方（事前の思い込み）は残る | 前進テストで hold を含めて評価する。プロンプトで「提供データのみに基づく」ことを維持する |
| セキュリティ | APIキーの漏えい、外部テキストからのプロンプトインジェクション | キーは `.env` に置き git 管理しない。paper 用と live 用でキーを分ける。モデルに執行権限を与えない構造を維持する |
| 法規（発信・副業化する場合） | 自分の口座だけの運用と、シグナルやシステムを他者に提供・販売することは別の問題 | 他者向けに出す場合は、金融商品取引法上の投資助言・代理業の登録が必要かを専門家に確認する【要確認】 |
| 実資金時の税・為替 | 米国株の課税関係、為替コスト、特定口座かどうか | Phase 6 で実資金を検討する場合に確認する【要確認】 |
| 日本株への展開 | Alpaca は米国株のみ | 国内証券会社の発注API（提供条件・費用）は未調査【要確認】 |

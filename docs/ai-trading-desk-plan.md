## 1. 目的・範囲

| 区分 | 内容 |
|---|---|
| 目的 | 保有銘柄とウォッチリストについて、株価・適時開示・法定開示を毎日読み、**朝の市場オープン前にブリーフ（要約と警告）を届ける**。後段では、構造化された投資仮説（thesis）と注文票を出し、仮想台帳で前進テストする |
| 対象外 | 発注の自動化（判断ゲートまで）、場中のリアルタイム監視、信用取引・空売り・デリバティブ、他者へのシグナル配信 |
| 責任境界 | AI は**読む・要約する・推奨する**まで。数量はコード（リスクエンジン）が計算し、**発注するかどうかと入力は本人**が行う |

### 1.1 日本株にすると「24/7」の意味が変わる

東証の立会時間は 9:00〜11:30 と 12:30〜15:30（2024-11-05 から大引けが15:30に延長。15:25〜15:30 はクロージング・オークション）。米国株と違い、**日本時間の日中に市場が開いている**。そのため、次の日次サイクルで足りる。家庭の時間とも衝突しにくい。

```
15:30 大引け
  ↓  （適時開示は大引け前後〜夕方に集中する）
夜   引け後ジョブ：株価・開示を取得 → 差分検知 → 開示要約（Batch）を投入
  ↓
朝   朝ジョブ（例 7:00）：Batch 結果を回収 → 朝ブリーフ作成（→ Phase 3以降は thesis・注文票も）
  ↓
8:00頃 本人がブリーフを確認 → 必要なら寄り付き前に手動で発注
  ↓
9:00 寄り付き
週末 週次レビュー（仮想台帳と判断の記録）
```

場中にAIを回す必要はない（場中の監視が要るのは逆指値くらいで、これは証券会社側の注文で代替する）。

## 4. システム構成

### 4.1 役割分担

```
[取得]  J-Quants（株価・財務・決算予定・カレンダー）/ EDINET / (TDnet アドオン) / 手動投入フォルダ
   │ 差分検知（新しい開示、閾値を超える値動き、決算予定日の接近）
   ▼
[読む]  claude-sonnet-5-5（Batch API・夜間）：開示ごとの構造化要約
   ▼
[まとめる]  claude-opus-5-5（朝）：朝ブリーフ ／ Phase 3以降は TradeThesis（構造化出力）
   │ ここまでが「リサーチデスク」（Phase 2で完成）
   ▼
[決める]  リスクエンジン（純Python、risk.yaml の変数で判定・数量計算）← AIは関与しない
   ▼
[出す]  注文票（CSV / Markdown）→ 本人が判断して手動で発注
   ▼
[記録]  仮想台帳（翌営業日以降の日足で約定を判定）＋ 判断ジャーナル（本人が実際に発注したかも記録）
```

### 4.2 リサーチデスク（Phase 2）の出力

1. **朝ブリーフ（Markdown、ブラウザで閲覧）**: 前日の引け後〜当朝までに出た保有銘柄・ウォッチ銘柄の開示要約、決算発表予定（今後5営業日）、異常値の警告
2. **警告（ルールで検知し、AIが説明を付ける）**: 業績予想の下方修正、減配・無配、大量保有報告書の提出や変更、株価の急変（変数で閾値を設定）、自分で決めた投資ルールへの抵触（例: 1銘柄の比率超過）
3. **一覧表（CSV、Excel で開く）**: 銘柄ごとの直近の開示件数、警告フラグ、要約へのリンク。文字化けを防ぐため UTF-8（BOM付き）で出力する

要約の正確性が肝になるため、**要約に含まれる数値は原文から機械的に抽出した値と照合し、一致しない場合は警告を付ける**（売上・利益・配当の金額など）。

### 4.3 Thesis（Phase 3）の日本株版スキーマ（案）

| フィールド | 内容 |
|---|---|
| `code` | 銘柄コード（**英字を含む新形式のコードにも対応**する。例: 130A） |
| `action` | `buy`（現物の新規買い）／ `exit`（保有株の決済）／ `hold`。空売りは受け付けない（v1 の欠陥Aへの対処） |
| `entry_limit` | 指値（寄り付き前に入力する前提） |
| `stop_loss` | 逆指値（仮説が誤りだと判断する価格） |
| `invalidation` | 仮説が誤りだと判明する条件 |
| `horizon_days` | 想定保有期間 |
| `sources` | 根拠にした開示や資料（ID・URL） |
| `confidence` | low / medium / high |

### 4.4 仮想台帳の約定ルール（すべて純コードで、過去データでテストできる）

- 指値の買い: 翌営業日の安値が指値以下なら、指値で約定したとみなす。始値が指値より下なら始値で約定とみなす
- 逆指値: 安値が逆指値以下なら発動。**始値がすでに逆指値より下（ギャップダウン）の場合は始値で約定**とみなし、損失が想定を超えたことを記録する
- **値幅制限（ストップ安）で約定しない可能性**があるため、ストップ安で張り付いた日は「不約定」として扱う（判定方法は J-Quants の提供項目を見て決める。【要確認】）
- 手数料・税は変数として持つ（初期値0。本人の口座条件に合わせて設定する）

### 4.5 実行環境（Windows）

- Python（venv）＋ タスクスケジューラ。各ジョブは1回実行して終わる。
- タスクスケジューラの「タスクを実行するためにスリープを解除する」を設定し、夜間・早朝のジョブでPCを起こす。PCが落ちていた場合は、次回起動時に未実行分を検知して追いかけ実行する。
- APIキー（Anthropic、J-Quants、EDINET）は `.env` か Windows の資格情報マネージャーに保存し、git 管理しない。
- 休場日は J-Quants の取引カレンダーで判定してスキップする。

## 5. リスク変数の設計（D4）

### 5.1 設定ファイル（初期値は記事どおり）

```yaml
# config/risk.yaml
version: 1
changed_at: 2026-10-16
change_reason: "初期値（記事どおり）"

max_position_pct: 0.05        # 1銘柄の上限（評価額に対する比率）
max_risk_per_trade_pct: 0.01  # 1回の取引で許容する損失（評価額に対する比率）
max_daily_loss_pct: 0.03      # 1日の損失がこれを超えたら翌日の新規提案を停止
max_open_positions: 5         # 同時に保有する銘柄数の上限（このシステム経由のもの）

lot_mode: unit                # unit=単元株（100株単位） / odd_lot=単元未満株（1株単位）
equity_source: manual         # 評価額の取得元：manual=本人が週1回入力 / ledger=仮想台帳
cooldown_days_after_exit: 5   # 決済後に同じ銘柄を再提案しない日数
```

### 5.2 変更のルール

- **引き下げ（厳しくする方向）はいつでも可能**。ファイルを書き換えれば、次回のジョブ実行から反映される。
- **引き上げ（緩める方向）には上限を設ける**。コード側にハードシーリング（初期値＝記事の値）を持ち、それを超える値が設定されていたらジョブを止めてエラーにする。上限自体を上げるにはコードの変更とコミットが必要になる。記事の「ルールは事前に決める。その場で決めるルールは気分にすぎない」をコードで担保する。
- 値の範囲・型・相互関係を起動時に検証する（例: 比率は0より大きく1未満、`max_risk_per_trade_pct` ≤ `max_position_pct`）。
- 変更のたびに `version` と `change_reason` を更新し、git に履歴を残す。ジャーナルには毎回 `risk.yaml` のハッシュを記録し、**どのルールでその判断が出たか**を後から追えるようにする。

### 5.3 日本株での計算例（単元株の影響）

数量は「1回の損失上限から決まる株数」と「1銘柄の上限から決まる株数」の小さい方とし、さらに単元に切り下げる。

前提（仮定）: 株価 ¥3,000、逆指値 ¥2,850（1株あたりのリスク ¥150）

| 評価額 | 損失上限から決まる株数 | 1銘柄上限から決まる株数 | 小さい方 | 単元（100株）に切り下げ | 単元未満株を使える場合 |
|---|---|---|---|---|---|
| ¥5,000,000 | 0.01×5,000,000÷150 = 333 | 0.05×5,000,000÷3,000 = 83 | 83 | **0株 → 提案不成立** | 83株 |
| ¥10,000,000 | 0.01×10,000,000÷150 = 666 | 0.05×10,000,000÷3,000 = 166 | 166 | **100株** | 166株 |

示唆: 100株単位だと、評価額が小さいほど「1銘柄5%」の制約で買える銘柄が限られる。**単元未満株を使うかどうか（lot_mode）は、評価額と取引する銘柄の株価帯を見て本人が決める**（§9 Q2）。

### 5.4 手動運用での「1日の損失3%」

手動運用では場中の損益をシステムが把握できないため、次のように運用する。
- 仮想台帳と、本人が入力した評価額をもとに、**前営業日の損失が3%を超えていたら、当日は新規の提案を出さない**（決済の提案は出す）。
- 場中の損切りは、証券会社に置いた逆指値注文に任せる。

## 6. 記事のサンプルコードの欠陥（v1 の §2.3）の扱い

| v1 の欠陥 | v2 での扱い |
|---|---|
| A 空売りの暴発 | スキーマで `exit` を「保有株の決済」に限定し、空売りを表現できなくする |
| B 同一銘柄の二重発注 | 保有中・注文票の出力済み・冷却期間中（`cooldown_days_after_exit`）の銘柄は提案しない |
| C 約定価格のずれ・ギャップ | 指値を前提にし、仮想台帳でギャップによる損失超過を記録する。値幅制限による不約定も考慮する |
| D キルスイッチの遅延 | 手動運用では、`KILL` ファイルがあると全ジョブが提案を出さなくなる仕組みに簡素化する（発注はそもそも本人が行う） |
| E 例外・応答拒否 | ジョブ単位で失敗を記録し、次回に再実行する。AI の応答拒否（refusal）や解析の失敗は hold として扱う |
| F 再現できない記録 | 入力、プロンプトの版、risk.yaml のハッシュ、トークン使用量を記録する |
| G 隔離タグ | ID を長くし（`token_hex(8)`）、本文中のタグ文字列を除去する。開示PDFやニュースは第三者の文章として扱う |
| H 評価できない | hold を含むすべての thesis を、事後の値動きで評価する |
| I コスト | 差分検知で、新しい情報がある銘柄だけを AI に渡す |

## 8. 評価方法

- **リサーチデスク（Phase 2）**: ブリーフが届いた割合、要約の数値の一致率、見逃した重要開示の件数（本人が気づいたのにブリーフに無かったもの）、1日あたりのコスト、本人が「役に立った」と判断した件数（週次で記録する）
- **Thesis（Phase 4）**: hold を含むすべての提案について、N営業日以内に invalidation の条件や逆指値に当たった割合と、その後の値動き。リスクエンジンの却下理由の内訳。比較対象はウォッチリストの等金額保有と TOPIX 連動ETF
- **バックテストはしない**（LLM は学習データ経由で結果を知っている可能性がある）。純コード部分（仮想台帳の約定判定、リスク計算）は過去データでテストしてよい
- 8〜12週では統計的な結論には足りない。主目的は「プロセスが記録どおりに動くこと」の確認

## 10. リスク・注意点

| 観点 | 内容 | 対応 |
|---|---|---|
| 期待値の根拠 | 規律あるプロセスは収益を保証しない | リサーチデスクを主たる成果物にし、売買は判断ゲートの後に置く（D1） |
| NISA での短期売買 | NISA 口座で売ると、その枠が復活するのは翌年になる。短期売買は非課税枠を消費しやすい | 注文票に口座区分（NISA／特定）の欄を設け、短期の thesis は特定口座を前提にする。どの口座で発注するかは本人が決める |
| 値幅制限・ギャップ | 逆指値でも損失が1%で止まるとは限らない | 仮想台帳でこれを再現し、損失超過を記録する |
| 要約の誤り | 数値の取り違えは判断を誤らせる | 原文の数値との機械照合（§4.2）と、本人による抜き取り確認 |
| プロンプトインジェクション | 開示文書の中の文言でモデルの判断が歪む可能性 | 隔離タグに加え、AI に数量計算と発注の権限を持たせない構造を維持する |
| データ利用条件 | J-Quants・TDnet アドオンは個人利用が前提。出力を公開・配布すると規約に触れる可能性がある | 発信や副業に使う場合は、利用規約と金融商品取引法（投資助言・代理業）の両方を確認する【要確認】 |
| PC の可用性 | スリープ、停電、Windows Update による再起動 | スリープ解除の設定、追いかけ実行、ブリーフが届かなかった日の通知 |
| 運用負荷 | 毎朝の確認が負担になる可能性 | ブリーフは要点を先頭にまとめる。警告がない日は「異常なし」の1行だけにする |

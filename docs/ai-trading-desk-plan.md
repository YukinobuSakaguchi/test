## 1. 目的・範囲

| 区分 | 内容 |
|---|---|
| 目的 | (1) 保有銘柄とウォッチリスト（約20銘柄）の株価・開示を毎日読み、**6:00に朝ブリーフ（要約と警告）を作る**。(2) **毎週、全上場銘柄から候補を絞り込んで提案する**。(3) 後段で、投資仮説（thesis）と注文票を出し、仮想台帳で前進テストする |
| 対象外 | 発注の自動化（判断ゲートまで）、場中のリアルタイム監視、信用取引・空売り、他者へのシグナル配信、TDnet 本文の自動取得 |
| 責任境界 | AI は「読む・要約する・提案する」まで。数量の計算と絞り込みはコードが行う。**銘柄を採用するか、発注するかは本人**が決める |

### 1.1 1日・1週間の流れ（日本時間）

```
15:30        大引け
夜（例 20:00） 夕方ジョブ：株価・財務・EDINET を取得 → 差分検知 → 開示の要約を Batch に投入
             （J-Quants の更新時刻が未確認のため、取得できなければ 23:00 に再試行する）
5:50         PC をスリープから起こす
6:00         朝ジョブ：Batch の結果を回収（未完了分は通常のAPI呼び出しで処理）→ 朝ブリーフ作成
～7:00       本人が確認 → 必要なら手動で注文
9:00         寄り付き（かぶミニの寄付取引はこの価格で約定する）
土曜 6:00     週次ジョブ：銘柄提案、仮想台帳の週次評価 → 週末に確認
```

## 2. データ源（TDnet アドオンなし）

| データ | 取得元 | 用途 | 判定 |
|---|---|---|---|
| 全上場銘柄の日足・銘柄一覧・取引カレンダー | J-Quants ライト（¥1,650/月） | 株価の急変検知、仮想台帳の約定判定、銘柄提案の絞り込み | 【確認済み・JPX発表】日次データの更新時刻は【要確認】 |
| 決算短信の数値（実績・予想）、**業績予想の修正、配当予想の修正** | J-Quants の財務情報（`/fins/summary`。書類種別に `EarnForecastRevision`・`DividendForecastRevision` がある） | 下方修正・減配の検知、銘柄提案の財務条件 | 書類種別の存在は【確認済み・公式仕様ページ】。**ライトプランで取得できる範囲は【要確認】（Phase 0 で最初に確認する）** |
| 有価証券報告書・半期報告書・大量保有報告書・自己株券買付状況報告書 | EDINET API v2（無料） | 大量保有の変動、自社株買いの進捗、銘柄提案の精査 | 【確認済み・二次情報】 |
| 決算短信の本文、業績修正の理由、その他の適時開示 | **手動投入フォルダ** | 本人が楽天証券や TDnet の閲覧サービスで見つけたPDFやテキストを置けば取り込む | — |

**TDnet なしで失われるもの:** 決算短信の定性的な説明（業績修正の理由など）と、EDINET に出ない適時開示（株式分割の発表、提携、不祥事など）の**自動取得**。
**補い方:** 数値の変化（修正・減配）は J-Quants で検知し、ブリーフで「理由は未取得。原文の確認を推奨」と明示する。重要な開示は本人が手動投入フォルダに入れる。それでも不足すると判断した時点で、アドオンを再検討する（判断事項として残す）。

## 3. 単元未満株（楽天証券 かぶミニ）を前提にした設計

### 3.1 かぶミニについて分かっていること

| 事項 | 内容 | 判定 |
|---|---|---|
| 取引の種類 | **寄付取引**（前日夜〜朝に注文し、寄り付きの価格で約定）と**リアルタイム取引**（場中に約定） | 【確認済み・二次情報】 |
| コスト | 売買手数料は無料。**リアルタイム取引にはスプレッド0.22%**、寄付取引にはスプレッドなし | 【確認済み・二次情報】 |
| 指値 | リアルタイム取引で利用可能（2024-08 追加） | 【確認済み・楽天プレスリリース】 |
| **逆指値** | **かぶミニで使えるかは確認できなかった** | **【要確認】設計に大きく影響する** |
| 口座区分 | 特定・一般・NISA 成長投資枠で利用可能 | 【確認済み・二次情報】 |
| 寄付取引の注文締切時刻 | 7:00 の確認後に注文が間に合うかに関わる | **【要確認】** |
| マーケットスピード II RSS からかぶミニを発注できるか | 自動化の判断に関わる | 【要確認】判断ゲートで確認 |

### 3.2 逆指値が使えない場合の影響と対処

記事の設計は「逆指値を証券会社側に置き、システムが止まっても損切りが効く」ことを前提にしている。かぶミニで逆指値が使えない場合、**場中に損切りが自動で効かず、1回の取引の損失が1%を超えうる**。対処は次の3つを組み合わせる。

1. **日次の監視:** 朝ジョブで、前日終値が `stop_loss` を割った保有株を検知し、朝ブリーフの先頭に「決済推奨（寄付取引で売り）」として出す。損切りは最大で1営業日遅れる。
2. **数量計算に余裕を持たせる:** 新しいリスク変数 `stop_execution_buffer_pct` を設け、数量計算に使う1株あたりのリスクを「エントリー価格と逆指値の差＋エントリー価格×バッファ」にする（初期値の案は 0.02。§6.1）。
3. **場中の通知:** 楽天のアプリの株価アラート（通知）が使えるなら、注文票と一緒に「アラートを設定する価格」を出す（機能の有無は【要確認】）。

逆指値が使えると確認できた場合は、1は保険として残し、2の初期値を下げる。

### 3.3 注文票（楽天 かぶミニ用）

楽天の注文画面の入力順に並べる（項目名は Phase 0 で実際の画面を見て合わせる）。

| 項目 | 例 |
|---|---|
| 銘柄コード／銘柄名 | XXXX／（銘柄名） |
| 売買 | 買い |
| 取引の種類 | 寄付取引 ／ リアルタイム取引 |
| 注文方法 | 成行（寄付取引）／ 指値（リアルタイム取引） |
| 価格 | 指値の場合のみ |
| 株数 | 83 |
| 口座区分 | 特定 ／ NISA 成長投資枠（**短期の thesis は特定を既定にする**） |
| 損切りライン（監視用） | 2,850円（朝ジョブの監視と、アプリのアラートに使う） |
| 根拠 | thesis ID、出典 |

### 3.4 仮想台帳の約定ルール（かぶミニ版）

- 寄付取引: 翌営業日の**始値で約定**とみなす（スプレッドなし）
- リアルタイム取引の指値買い: 安値が指値以下なら指値で約定とみなし、**スプレッド0.22%を加える**
- 損切り: 終値が `stop_loss` を下回った翌営業日の始値で売却とみなす（§3.2 の日次監視と同じ）。損失が想定を超えた場合は記録する
- 値幅制限で寄り付かなかった日は不約定とみなす（判定方法は J-Quants の項目を見て決める。【要確認】）
- スプレッド・手数料・税は変数で持つ

## 4. システム構成

### 4.1 全体像

```
[取得]  J-Quants（日足・財務・カレンダー：全銘柄）/ EDINET / 手動投入フォルダ / 投資管理アプリのCSV
   │ 差分検知
   ▼
[読む]  claude-sonnet-5-5（Batch・夜間）：開示ごとの構造化要約
   ▼
[まとめる]  claude-opus-5-5（6:00）：朝ブリーフ        claude-opus-5-5（土曜）：銘柄提案カード
   │                                                 ↑ コードで全銘柄を絞り込み（screen.yaml）
   │  ここまでが「リサーチデスク」（Phase 2A・2B）
   ▼
[決める]  リスクエンジン（純Python、risk.yaml）← AIは関与しない
   ▼
[出す]  注文票（楽天 かぶミニ形式）→ 本人が判断して手入力
   ▼
[記録]  仮想台帳 ＋ 判断ジャーナル（採否と理由、実際に発注したか）
```

### 4.2 朝ブリーフの構成（7:00 までに読み切れる量にする）

1. **要対応（あれば先頭に）:** 損切りラインの割り込み、業績予想の下方修正・減配、比率上限の超過、大量保有の変動。なければ「要対応なし」の1行だけ
2. 保有・ウォッチ銘柄の新しい開示の要約（数値は原文から機械的に取り出した値と照合し、合わない場合は警告を付ける）
3. 今後5営業日の決算発表予定
4. （Phase 3 以降）注文票の候補

### 4.3 投資管理アプリの CSV 取り込み（D8）

- 取り込みフォルダに置かれた最新の CSV を読み込む。**列の対応は `import_map.yaml` で定義**し、アプリ側の形式が変わっても設定ファイルの修正だけで済むようにする。
- 取り込む項目（案）: 基準日、銘柄コード、株数、取得単価、評価額、口座区分（NISA／特定）、現金残高（あれば）
- 検証: 必須の列があるか、銘柄コードの形式（英字を含む新形式も可）、評価額の合計、基準日が古すぎないか（変数で閾値を設定）。不備があれば取り込みを止めて朝ブリーフで知らせる。
- 用途: 評価額（リスク計算の基準）、比率上限の監視、保有株の損切り監視、銘柄提案で保有中の銘柄を除外すること。
- 文字コードは Shift_JIS と UTF-8 の両方に対応する。
- 逆方向（このシステムの出力を投資管理アプリに取り込む）も、必要なら CSV で出せる形にしておく。

### 4.4 実行環境（Windows）

- Python（venv）＋ タスクスケジューラ。各ジョブは1回実行して終わる。
- 「タスクを実行するためにスリープを解除する」を有効にする（5:50 と夕方）。PCが落ちていた場合は、次の起動時に未実行分を追いかけて実行する。
- APIキーは `.env` か Windows の資格情報マネージャーに置き、git 管理しない。

### 4.5 Batch と 6:00 の締切

- Anthropic の Batch API は「ほとんどが1時間以内に完了、最大24時間」とされている（公式ドキュメント）。夕方に投入すれば通常は 6:00 に間に合う。
- 6:00 の時点で未完了の分は通常のAPI呼び出し（料金は Batch の2倍）で処理し、ブリーフの作成を遅らせない。未完了だった件数は記録する。

## 5. 銘柄提案（D9・Phase 2B）

### 5.1 方式：コードで絞り込み、AI で精査する

| 段階 | 処理 | 担当 | 頻度 |
|---|---|---|---|
| 1 絞り込み | 全上場銘柄（約3,900）を `screen.yaml` の条件で機械的に絞る | 純コード | 毎週土曜 |
| 2 順位付け | 条件の満たし方でスコアを付け、上位N件（例: 30件）を残す | 純コード | 〃 |
| 3 精査 | 上位の数件（例: 10件）について、財務の推移・直近の開示・EDINET の資料を読み、**提案カード**を作る | claude-opus-5-5（構造化出力） | 〃 |
| 4 採否 | 本人が読み、ウォッチリストに加えるかを決める。採否とその理由を記録する | **本人** | 週末 |

保有中の銘柄、ウォッチ中の銘柄、最近見送った銘柄（変数で期間を設定）は候補から除く。

### 5.2 絞り込み条件（初期値の案。すべて変数）

長期保有・配当を重視する方向に寄せた初期値の案。最終的な条件は本人が決める（§11 Q3）。

```yaml
# config/screen.yaml（案）
universe:
  markets: [prime, standard]     # 市場区分
  exclude_types: [etf, reit]
liquidity:
  min_avg_turnover_jpy: 100_000_000   # 20日平均の売買代金の下限
  min_market_cap_jpy: 30_000_000_000  # 時価総額の下限
dividend:
  min_forecast_yield: 0.03           # 予想配当利回り
  max_payout_ratio: 0.70             # 配当性向の上限
  no_dividend_cut_years: 5           # 直近5年に減配なし（データで判定できる範囲で）
fundamentals:
  max_per: 20
  max_pbr: 2.0
  exclude_recent_downward_revision_days: 90   # 直近90日に業績予想の下方修正があれば除外
output:
  shortlist_size: 30
  deep_dive_size: 10
```

各条件がライトプランのデータで判定できるかは Phase 0 で確認する（例: 5年分の減配履歴、自己資本比率）。判定できない条件は外すか、EDINET で補う。

### 5.3 提案カード（AI が出す内容）

| 項目 | 内容 |
|---|---|
| 銘柄・業種・現在値・予想配当利回り | 数値はコードで埋める（AI に計算させない） |
| 提案の理由 | 根拠となる数値と開示を明記する |
| **主なリスクと反対の見方** | 「この銘柄を選ばない理由」を必ず書かせる |
| 誤りだと判断する条件（invalidation） | 例: 減配、配当性向が○%を超える |
| 出典 | 使ったデータ・書類のID |
| 確度 | low / medium / high |

### 5.4 銘柄提案の評価

- 提案した銘柄（**採用・見送りの両方**）のその後のトータルリターン（配当込み）を TOPIX 連動ETF と比べる（前進テスト）。
- 絞り込みの条件（純コード）は過去データで検証してよい。ただし、現在上場している銘柄だけで検証すると、上場廃止になった銘柄が抜け落ちて成績がよく見える偏り（生存者バイアス）がある。J-Quants に上場廃止銘柄が含まれるかは【要確認】。
- AI による精査は**バックテストしない**（学習データ経由で結果を知っている可能性がある）。

## 6. リスク変数（D4・D7 を反映）

### 6.1 risk.yaml（初期値）

```yaml

changed_at: 2026-10-16
change_reason: "初期値（記事どおり＋単元未満株・逆指値なしへの対応）"

max_position_pct: 0.05          # 1銘柄の上限（評価額比）               ※記事どおり
max_risk_per_trade_pct: 0.01    # 1回の取引の許容損失（評価額比）        ※記事どおり
max_daily_loss_pct: 0.03        # 前営業日の損失がこれを超えたら新規提案を停止  ※記事どおり
max_open_positions: 5           # このシステム経由で同時に持つ銘柄数     ※記事どおり

lot_mode: odd_lot               # 単元未満株（1株単位）                  ※D7

spread_realtime_pct: 0.0022     # かぶミニのリアルタイム取引のスプレッド
cooldown_days_after_exit: 5     # 決済後に同じ銘柄を再提案しない日数
equity_source: portfolio_csv    # 評価額の取得元                          ※D8
```

### 6.2 変更のルール

- **引き下げ（厳しくする方向）は自由。** ファイルを書き換えれば次のジョブから反映される。
- **引き上げはコード側の上限（ハードシーリング：記事の値）まで。** 上限を超える値が書かれていたらジョブを止めてエラーにする。上限自体を変えるにはコードの変更とコミットが必要。
- 起動時に値の範囲と相互関係を検証する（例: `max_risk_per_trade_pct` ≤ `max_position_pct`）。
- 変更のたびに `version` と `change_reason` を更新し、ジャーナルには毎回 `risk.yaml` のハッシュを記録する。

### 6.3 計算例（単元未満株）

前提（仮定）: 評価額 ¥5,000,000、株価 ¥3,000、損切りライン ¥2,850

- バッファなし: 損失上限から決まる株数 = 0.01×5,000,000÷150 = 333株、1銘柄上限から決まる株数 = 0.05×5,000,000÷3,000 = 83株 → **83株**（v2 の100株単位では0株だったものが、単元未満株で成立する）
- バッファ 2% を含める: 1株あたりのリスク = 150 + 3,000×0.02 = 210円 → 0.01×5,000,000÷210 = 238株。1銘柄上限は83株のまま → **83株**（この例では1銘柄上限の方が先に効く）
- リアルタイム取引で買った場合のスプレッド: 3,000×83×0.0022 ≈ **548円**。寄付取引ならかからない

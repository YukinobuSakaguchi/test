# 第1部 入門編（コード・ターミナル不要）

## 1. 「チャット」と「エージェント」の違い

> この章でわかること: Skillが活躍する「AIエージェント」とは何か。

ChatGPTに質問すると、文章で答えが返ってきます。これが「**チャット**」としての使い方です。
AIは答えを書きますが、実際の作業（ファイルを作る、表を計算する、調べ物を何度も繰り返す）はあなたが行います。

最近のAIは、もう一歩進んで「**作業そのもの**」も行えるようになりました。

- Excelファイルを読み込み、集計して、グラフ付きの新しいファイルを作る
- Webを何度も検索し、結果を比べて、報告書にまとめる
- プログラムを書き、動かし、エラーが出たら直す

このように、**道具（ファイル操作、Web検索、プログラム実行など）を使いながら、目的を達成するまで自分で手順を進めるAI**を「**AIエージェント**」と呼びます。

| | チャット | エージェント |
|---|---|---|
| AIがすること | 質問に文章で答える | 道具を使って作業を進め、成果物を作る |
| 人がすること | 答えを読んで、自分で作業する | 目的を伝え、結果を確認する |
| 例 | 「議事録の書き方を教えて」 | 「このメモから議事録ファイルを作って」 |

この文書で扱う5つの環境は、どれもエージェントとして働けます。

- **Claude.ai**: Anthropic社のAI「Claude」をブラウザやアプリで使うサービス
- **ChatGPT**: OpenAI社のAIサービス
- **Claude Code**: Claudeをパソコン上で開発作業に使うためのツール
- **OpenAI Codex**: OpenAI社の開発作業向けエージェント
- **GitHub Copilot**: GitHub社（Microsoft傘下）の開発支援AI

## 2. Skillとは

> この章でわかること: Skillが何を解決するのか、どんなときに役立つのか。

### 新人に渡す「業務マニュアル」

AIは賢いですが、**あなたの職場のやり方**は知りません。

たとえば議事録を頼むたびに、次のように毎回説明していないでしょうか。

> 「決定事項と宿題を分けて書いて。宿題には担当と期限を必ず入れて。書式はいつもの形で……」

新人に仕事を頼むとき、毎回口頭で説明する代わりに**業務マニュアル**を渡しますよね。
**Skillは、AIに渡す業務マニュアルです。**

一度作っておけば、AIは「議事録にして」と言われた時点で自分からマニュアルを開き、そのとおりに作業します。

### Skillが役立つ場面

| 場面 | Skillにしておくこと |
|---|---|
| 議事録の作成 | 決まった見出し、宿題の書き方、確認の手順 |
| 定型メール | 社内の言い回し、署名、宛先ごとの敬語の使い分け |
| 報告書のチェック | 確認項目の一覧、よくあるミス、指摘の書き方 |
| 資料作成 | 会社のフォント・色・ロゴの使い方 |
| データ集計 | 列の意味、除外すべきデータ、計算方法 |

目安として、**同じ説明をAIに3回以上したことがある作業**は、Skillにする価値があります（これは本書の推奨で、公式の基準ではありません）。

### 必要なときだけ読まれる

Skillをたくさん登録しても、AIの動きは重くなりにくい仕組みになっています。

AIはふだん、各Skillの「**名前**」と「**いつ使うかの説明**」だけを覚えています。
頼まれた作業に合うSkillがあったときだけ、その中身を読みます。
本棚の背表紙だけを眺めておき、必要な本だけを取り出して読むイメージです。

### どのAIでも同じ形式

2026年10月時点で、この文書で扱う5つの環境はいずれも「**Agent Skills**」という共通の形式に対応しています。
そのため、一度作ったSkillは、少しの手直しで別のAIでも使えます（詳しくは[11章](#11-複数の環境で使い回すコツ)）。

## 3. Skillの中身をのぞいてみる

> この章でわかること: Skillファイルの最小構成と、各行の意味。

Skillの正体は、**`SKILL.md` という名前のテキストファイル1つ**です（それを入れたフォルダごと扱います）。
`.md` は「Markdown（マークダウン）」という書き方のテキストファイルを表します。
Markdownは、`#` で見出し、`-` で箇条書きを表すなど、記号で文章の構造を示すシンプルな書き方です。メモ帳でも書けます。

もっとも小さなSkillの例です。

```markdown
---
name: meeting-minutes
description: 会議のメモから議事録を作る。「議事録にして」と頼まれたときに使う。
---

# 議事録の作成

1. 決定事項・宿題・未決事項に分けて書く。
2. 宿題には担当と期限を必ず書く。わからなければ「要確認」と書く。
3. 最後に、確認が必要な点を一覧にする。
```

大きく3つの部分に分かれています。

| 部分 | 中身 | たとえると |
|---|---|---|
| `name:` の行 | Skillの名前（半角英小文字とハイフン） | マニュアルの背表紙のタイトル |
| `description:` の行 | 何をするSkillで、**いつ使うか** | 背表紙の「こんなときに読む」 |
| `---` より下 | 実際の手順 | マニュアルの本文 |

上の `---` で囲まれた部分を「**フロントマター**」と呼びます。ファイルの先頭に置く「表紙情報」です。
書き方は「YAML（ヤムル）」という形式で、`項目名: 値` の形で書きます。

いちばん大切なのは `description` です。
AIはこの説明文だけを見て「今の頼みごとにこのSkillを使うべきか」を判断します。
「何をするか」と「どんな頼み方をされたら使うか」の両方を書くのがコツです。

## 4. はじめてのSkillを作る（ハンズオン）

> この章でわかること: コードを書かずに、最初のSkillを作って動かす手順。

いちばん簡単なのは、**AIに頼んでSkillを作ってもらう**方法です。
ChatGPTには、Skill作りを手伝う「skill-creator」というSkillが最初から用意されています。
Claude.aiでも、Anthropicが用意した例のSkill（skill-creatorを含む）をオンにして使えます。なお、Anthropicの公式ガイドによれば、特別な準備をしなくても「Skillを作って」と頼むだけで、Claudeは正しい形式のSkillを作れます。

### 方法A: Claude.aiで作る

**対象プラン**: Free / Pro / Max / Team / Enterprise（公式ヘルプより）

1. **準備**: 「設定（Settings）」→「機能（Capabilities）」で「**コード実行とファイル作成**（Code execution and file creation）」をオンにします。
   Skillはこの機能を使って動くため、オフだと使えません。
   - Team / Enterpriseプランでは、組織の管理者がSkillを有効にしている必要があります。
2. **頼む**: 新しいチャットで、次のように頼みます。

   ```
   議事録を作るSkillを作ってください。
   会議メモを貼ったら、決定事項・宿題（担当と期限）・未決事項に分けて、
   いつも同じ書式で出してほしいです。
   ```

3. **答える**: Claudeが「どんな書式がよいか」「どんな言葉で頼んだら使うか」などを質問してきます。わかる範囲で答えます。
4. **保存する**: できあがったSkillがファイルとして表示されます。
   - 「**Save skill**」ボタンが表示されれば、押すだけで登録できます（組織の設定によっては表示されません）。
   - ボタンがない場合は、ファイルをダウンロードしてから、後述の「方法C」の手順5〜6でアップロードします。
5. **確認する**: 「**カスタマイズ（Customize）」→「スキル（Skills）**」を開き、作ったSkillがオンになっていることを確認します。
6. **試す**: **新しいチャット**で会議メモを貼り、「議事録にして」と頼みます。
   回答の途中にSkillを読み込んだことが表示されれば成功です。

### 方法B: ChatGPTで作る

**対象プラン**: 公式ヘルプでは、ChatGPT Business / Enterprise / Healthcare / Edu の対象ユーザーが利用でき、ワークスペースの設定にも左右されるとされています。
Plus / Pro の個人プランについては情報が分かれています（**要確認**）。

1. ChatGPTの「**Skills**」画面を開きます（「Plugins」の中のSkillsタブにあるという情報があります。画面構成は**要確認**）。
2. 「**Create**」を選び、次のいずれかを選びます。
   - **Create with chat**: チャットで相談しながら作る（はじめての人におすすめ）
   - **Create with editor**: エディタで直接書く
   - **Upload from your computer**: 作ってあるSkillをアップロードする
3. 「Create with chat」を選んだ場合は、方法Aの手順2〜3と同じように、作りたいSkillを説明し、質問に答えます。
4. 保存したら、新しいチャットで試します。

アップロードしたSkillは、利用可能になる前にChatGPT側で安全性のチェックが行われます。チェックの結果、確認待ちやブロックになる場合があります。

### 方法C: 自分で書いてアップロードする（Claude.aiの例）

AIに頼まず、自分で書くこともできます。Windowsの「メモ帳」で作れます。

1. デスクトップなどに `meeting-minutes` という名前の**フォルダ**を作ります。
2. メモ帳を開き、[3章](#3-skillの中身をのぞいてみる)の例をそのまま貼り付けます。
3. 「名前を付けて保存」で、次のように保存します。
   - 保存先: 手順1のフォルダの中
   - ファイル名: `SKILL.md`（**大文字**で）
   - ファイルの種類: 「**すべてのファイル**」（「テキスト文書」のままだと `SKILL.md.txt` になってしまいます）
   - 文字コード: **UTF-8**
4. フォルダごとZIPファイルにします。**フォルダ自体**を右クリックし、「送る」→「圧縮（zip形式）フォルダー」を選びます（Windows 11では「ZIPファイルに圧縮する」）。
   - フォルダの**中身**を選んで圧縮すると、正しく読み込めません。ZIPを開くと `meeting-minutes` フォルダが入っている状態が正解です。
5. Claude.aiで「**カスタマイズ」→「スキル**」を開き、「**＋**」→「**＋ Create skill**」→「**Upload a skill**」を選びます。
6. 手順4のZIPファイルをアップロードします。一覧に表示され、オンになっていれば完了です。

### うまく動かないときの3つの確認点

1. **Skillがオンになっているか**: 一覧でスイッチがオフのままになっていないか確認します。
2. **頼み方の言葉が `description` に入っているか**: 「議事録」と書いてあっても、あなたが「打合せ記録」と頼むと使われないことがあります。よく使う言い方を `description` に足します。
3. **新しいチャットで試したか**: Skillを作った同じチャットでは、正しく試せないことがあります。

それでも使われないときは、「**議事録Skillを使って**」とはっきり名前を出して頼むと確実です。

## 5. カスタム指示・プロジェクト・GPTsとの違い

> この章でわかること: 似た機能との使い分け。

AIの動きを自分好みにする機能は、Skill以外にもあります。

| 機能 | 効く範囲 | 向いている内容 | 例 |
|---|---|---|---|
| カスタム指示（パーソナライズ） | すべての会話に毎回 | 短い好み・前提 | 「日本語で、結論から答えて」 |
| プロジェクト | そのプロジェクト内の会話 | 特定テーマの資料と指示 | 「新製品Xの資料一式」 |
| GPTs（ChatGPT） | そのGPTを選んだ会話 | 特定用途の専用チャット相手 | 「英文校正GPT」 |
| リポジトリの指示ファイル（`CLAUDE.md`、`AGENTS.md`、Copilotのカスタム指示など） | そのリポジトリでの作業すべて | 開発のルール・前提 | 「テストは必ず実行する」 |
| **Skill** | **必要なときだけ自動で** | **特定作業の詳しい手順** | 「議事録の作り方」 |

使い分けの考え方はシンプルです。

- **ほぼ毎回必要な短いこと** → カスタム指示や指示ファイル
- **特定の作業のときだけ必要な、詳しい手順** → Skill

GitHub Copilotの公式ドキュメントも、「ほぼすべての作業に関係する簡単な指示はカスタム指示に、関係するときだけ参照すべき詳しい指示はSkillに」と勧めています。

Skillには、ほかにない利点が2つあります。

- **何個登録しても邪魔になりにくい**: 中身は必要なときだけ読まれます。
- **持ち運べる**: 共通形式なので、別のAIサービスに移っても使えます。

# 第2部 実践編（自分で書いて、どの環境でも使う）

## 6. 共通ルール（Agent Skills標準）

> この章でわかること: どの環境でも通用するSkillの正式な形式。

各社のSkillは、オープンな仕様「Agent Skills」（agentskills.io）に基づいています。ここに合わせて書けば、どの環境でも動く土台ができます。

### フォルダ構成

```
meeting-minutes/          ← フォルダ名 = Skillの名前
├── SKILL.md              ← 必須: フロントマター + 手順
├── references/           ← 任意: 必要なときに読む詳しい資料
│   └── format.md
├── scripts/              ← 任意: 実行するプログラム
└── assets/               ← 任意: テンプレート、画像、データ
```

必須なのは `SKILL.md` だけです。ファイル名は大文字の `SKILL.md` にします（Copilotの公式ドキュメントは「`SKILL.md` という名前でなければならない」と明記しています）。

### フロントマターの項目

| 項目 | 必須 | 制約（Agent Skills仕様） |
|---|---|---|
| `name` | 必須 | 1〜64文字。半角の英小文字・数字・ハイフンのみ。先頭と末尾にハイフン不可。ハイフン連続（`--`）不可。**フォルダ名と一致させる** |
| `description` | 必須 | 1〜1024文字。何をするか、いつ使うかを書く |
| `license` | 任意 | ライセンス名、または同梱したライセンスファイル名 |
| `compatibility` | 任意 | 1〜500文字。必要な環境（対象製品、必要なソフト、ネット接続など）。ほとんどのSkillでは不要 |
| `metadata` | 任意 | 自由な「キー: 値」の組（例: `version: "1.0"`、`author: ...`） |
| `allowed-tools` | 任意 | 事前に許可するツールの一覧（実験的。対応は製品により異なる） |

### 環境ごとの追加の制約

仕様より厳しい制約を持つ環境があります。**どこでも通用させたいなら、いちばん厳しい条件に合わせます。**

| 環境 | 追加の制約・注意 |
|---|---|
| Claude（Claude.ai、API） | `name` に「anthropic」「claude」という語を含められない。`name`・`description` にXMLタグ（`<tag>` のような記述）を含められない |
| Claude.ai | 公式ヘルプの説明では `description` は**200文字以内**。アップロード時に使える項目は `name`、`description`、`license`、`compatibility`、`metadata`、`allowed-tools` のみで、それ以外の項目があるとエラーになる（Claude Codeのドキュメントより） |
| Claude Code | `description`（と `when_to_use`）は一覧表示の際に1,536文字で切られる。知らない項目は無視される |
| Copilot | フォルダ名は小文字、空白の代わりにハイフンを使う |

本書の推奨は次のとおりです。

- `name`: 英小文字とハイフンで、**動作がわかる名前**（`meeting-minutes`、`reviewing-reports` など）
- `description`: **200文字以内**（日本語でも同じ）

### 「段階的な読み込み」の仕組み

Skillは3段階で読み込まれます。これを「プログレッシブ・ディスクロージャー（段階的開示）」と呼びます。

```
段階1 発見   … 起動時に、全Skillの name と description だけ読む（1つあたり約100トークン）
   ↓ 頼みごとが description に合致
段階2 起動   … SKILL.md の本文を全部読む（5,000トークン未満を推奨）
   ↓ 本文に「詳しくは references/format.md」とあり、必要になった
段階3 実行   … 必要なファイルだけ読む・スクリプトを実行する
```

「トークン」はAIが文章を数える単位です。AIが一度に扱える情報量（コンテキスト）には上限があるため、普段は最小限だけ読み、必要に応じて詳細を読むようにできています。

このため、次の2点が重要になります。

- **`description` の出来が、Skillが使われるかどうかを決める**（段階1では本文が読まれないため）
- **`SKILL.md` は500行以内に収め、詳細は別ファイルに分ける**（段階2で全部読まれるため）

## 7. 良いSkillの設計手順

> この章でわかること: 書き始める前に決めておくこと。

いきなり書き始めるより、次の5点を先に決めると失敗が減ります。

### 手順1: Skillにすべき作業か判定する

| Skillに向く | Skillに向かない |
|---|---|
| 何度も繰り返す作業 | 一度きりの作業 |
| 手順やルールが決まっている | 毎回やり方が違う |
| AIが知らない社内ルールがある | AIが一般知識で十分こなせる |
| 1つの目的に絞れる | 「何でもできる」万能型 |

1つのSkillには1つの仕事を担当させます。大きなSkillを1つ作るより、**小さなSkillを複数作る**ほうがうまく組み合わさります（Anthropicの公式ヘルプでも推奨されています）。

### 手順2: 発動条件を決める

「どんな言葉で頼まれたら使うか」を、**実際の言い方**で5つ以上書き出します。

> 例: 「議事録にして」「会議メモをまとめて」「打合せ記録を作って」「さっきのミーティングの内容を整理して」＋文字起こしの貼り付け

### 手順3: 入力と出力を決める

- 入力: 何を受け取るか（貼り付けた文章、ファイル、URLなど）
- 出力: 何を返すか（書式、ファイル形式、長さ）

### 手順4: 成功の基準を決める

「できた」と言える条件を、確かめられる形で書きます。

> 例: 宿題が全件「担当・内容・期限」の3点そろっている／入力にない情報が書かれていない

### 手順5: テスト用の頼み方を3つ用意する

Skillが使われる「べき」頼み方を最低3つ用意します。Anthropicの公式ガイドも、少なくとも3つの評価シナリオを作ることを勧めています。

さらに、**使われる「べきでない」が紛らわしい頼み方**も用意すると、誤発動を防げます。

> 例: 「議事録の書き方のコツを教えて」（一般的な質問なのでSkill不要）

## 8. SKILL.mdの書き方

> この章でわかること: AIに伝わる `description` と本文の書き方。

### `description` の書き方

`description` は「何をするか」＋「いつ使うか」を書きます。

| | 例 | 評価 |
|---|---|---|
| 悪い例 | `議事録を手伝う。` | 何をするか曖昧。いつ使うかがない |
| 悪い例 | `私は議事録を作れます。` | 一人称は避ける（AIの判断材料として読まれるため） |
| 良い例 | `会議のメモや文字起こしから、決定事項・宿題（担当・内容・期限）・未決事項を整理した議事録を作成する。「議事録にして」「会議メモをまとめて」と頼まれたとき、または会議の文字起こしが貼り付けられたときに使う。` | 何を・いつが具体的。利用者の言葉が入っている |

書き方のコツです。

- **利用者が実際に使う言葉を入れる**: 「議事録」「会議メモ」「打合せ記録」など言い換えも入れます。
- **頼まれ方が明示的でない場面も書く**: 「〜が貼り付けられたとき」のように、状況でも判断できるようにします。
- **少し積極的に書く**: AIはSkillを使わずに済ませようとする傾向があるため、「〜という言葉がなくても、〜の場合は使う」と書き添えると使われやすくなります（Anthropic提供のskill-creatorの解説より）。
- **主語は書かない（三人称で書く）**: 英語の公式ガイドは三人称で書くよう求めています。日本語なら「〜する。〜のときに使う。」と書けば自然にそうなります。

### 本文の書き方

本文の形式に決まりはありません。次の構成が書きやすく、伝わりやすい形です。

```markdown
# （Skillの名前）

## 目的        ← 何を達成するか、誰が使うか
## 手順        ← 番号付きの手順
## 判断のルール ← 迷う場面での決め方と、その理由
## 出力の形式   ← 書式（長ければ references/ に分ける）
## 例          ← 入力と出力の具体例
```

書くときの原則です。

1. **AIがすでに知っていることは書かない**
   「議事録とは会議の記録である」といった一般的な説明は不要です。AIが知らない「あなたの職場のやり方」だけを書きます。
   本文は読まれた時点でAIの作業メモを占有するので、短いほど他の作業に余裕が残ります。
2. **理由を添える**
   「必ず〜すること」と強く書くより、「〜する。なぜなら〜だから」と理由を書くほうが、想定外の場面でもAIが正しく判断できます。
   大文字の「MUST」や「絶対に」を多用したくなったら、理由の説明が足りていないサインです。
3. **具体例を入れる**
   入力と出力の例を1〜3組入れると、説明文だけより正確に伝わります。
4. **自由度を作業に合わせる**
   やり方が何通りもある作業（文章の推敲など）は大まかな方針だけを書きます。
   手順を一つでも間違えると困る作業（決まった計算、書類の提出形式など）は、手順を細かく指定します。
5. **用語をそろえる**
   「宿題」「ToDo」「アクションアイテム」を混在させず、1つの言葉に統一します。
6. **時期で変わる情報を書かない**
   「2026年3月までは旧様式」のような記述は、時期が過ぎると誤りになります。現行のやり方だけを書き、古いやり方は「旧方式」として分けておきます。

### 付属ファイルの使い分け

| フォルダ | 入れるもの | AIの扱い | 例 |
|---|---|---|---|
| `references/` | 詳しい資料 | 必要なときに**読む** | 書式の詳細、用語集、社内規程の抜粋 |
| `scripts/` | プログラム | 必要なときに**実行する**（中身は読まなくてよい） | 集計、ファイル変換、チェック処理 |
| `assets/` | 素材 | 成果物に**使う** | Word/PowerPointのテンプレート、ロゴ画像 |

付属ファイルを使うときの注意です。

- `SKILL.md` から**直接**リンクします（例: `[書式](references/format.md)`）。資料からさらに別の資料へ…と何段階もたどらせると、AIが途中までしか読まないことがあります。
- パスの区切りは `/`（スラッシュ）を使います。Windowsの `\`（円記号・バックスラッシュ）は他の環境で動きません。
- ファイル名は中身がわかる名前にします（`doc2.md` ではなく `format.md`）。
- 100行を超える資料には、先頭に目次を付けます。

## 9. 環境別の登録方法

> この章でわかること: 5つの環境それぞれで、Skillをどこに置き、どう確かめるか。

### 比較表

| 環境 | 登録方法 | 置き場所 | 名前を指定して使う | 登録の確認 |
|---|---|---|---|---|
| **Claude.ai** | 画面からZIPをアップロード／チャットで作成 | アカウント（クラウド） | 自然な言葉で頼む（Excel等のアドインでは `/` で選択） | 「カスタマイズ」→「スキル」 |
| **ChatGPT** | チャットで作成／エディタ／アップロード | ワークスペース（クラウド） | 自然な言葉で頼む | Skills画面（**要確認**） |
| **Claude Code** | フォルダを置く | 個人: `~/.claude/skills/<名前>/`<br>プロジェクト: `.claude/skills/<名前>/` | `/<名前>` | `/skills` |
| **Codex** | フォルダを置く | 個人: `~/.agents/skills/<名前>/`<br>リポジトリ: `.agents/skills/<名前>/` | `$<名前>` | 頼んで確かめる |
| **GitHub Copilot** | フォルダを置く／`gh skill install` | 個人: `~/.copilot/skills/` または `~/.agents/skills/`<br>リポジトリ: `.github/skills/`、`.claude/skills/`、`.agents/skills/` | `/<名前>`（CLI） | `/skills list`（CLI） |

`~` は自分の「ホームフォルダ」を表します。Windowsなら通常 `C:\Users\<ユーザー名>` です。
「リポジトリ」は、プログラムや文書をまとめて変更履歴ごと管理する保管場所（主にGit/GitHub）です。

### 9.1 Claude.ai

**利用条件**: Free / Pro / Max / Team / Enterprise。「コード実行とファイル作成」が有効であること。

**登録**:

1. Skillフォルダを**フォルダごと**ZIPにします（ZIPの直下にSkillフォルダがある状態）。
2. 「カスタマイズ（Customize）」→「スキル（Skills）」→「＋」→「＋ Create skill」→「Upload a skill」でZIPをアップロードします。
3. 一覧でオンにします。

チャット中にClaudeが作ったSkillは、表示された「Save skill」ボタンから直接保存できる場合があります。

**チームでの共有**（Team / Enterprise）:

- 「…」メニュー →「Share」で、特定の人（Enterpriseはグループも）に共有できます。受け取った側は閲覧のみで、オンにすると使えます。作成者が更新すると、次回の利用時に自動で新しい版になります。
- 「Publish to org」で組織のライブラリに公開できます。組織の設定によっては、管理者のレビューを経て公開されます。

**その他**: Claude.aiで有効にしたSkillは、Claude for Excel / PowerPoint / Word / Outlook のアドインや、同じアカウントでログインしたClaude Codeでも使えます。

### 9.2 ChatGPT

**利用条件**: 公式ヘルプでは Business / Enterprise / Healthcare / Edu の対象ユーザー。ワークスペース管理者の設定に左右されます。個人向けプランの対応は**要確認**です。

**登録**:

1. Skills画面で「Create」を選びます。
2. 「Create with chat」「Create with editor」「Upload from your computer」から選びます。
3. アップロードの場合、ChatGPTの安全性チェックを通過すると利用可能になります。

**注意**:

- アップロードできるファイル形式（ZIPなど）の詳細は、公式資料で直接確認できませんでした（**要確認**）。Agent Skills形式のフォルダをZIPにしたものが一般的に案内されています。
- ワークスペース管理者は、アップロードを無効にできます。
- OpenAIの資料では、ChatGPTとCodexはどちらも「起動時は name と description だけを読み、使うと決めたときに SKILL.md 全体を読む」と説明されています。

### 9.3 Claude Code

**置き場所**:

| 範囲 | 場所 | 使える範囲 |
|---|---|---|
| 個人 | `~/.claude/skills/<名前>/SKILL.md` | 自分のすべてのプロジェクト |
| プロジェクト | `.claude/skills/<名前>/SKILL.md` | そのリポジトリ（コミットすればチームで共有） |
| プラグイン | `<プラグイン>/skills/<名前>/SKILL.md` | プラグインを有効にした場所（`/プラグイン名:スキル名` で呼ぶ） |

同じ名前のSkillがある場合は、組織（Enterprise）＞個人＞プロジェクトの順で優先されます。

**使い方**:

- 自動: 頼みごとが `description` に合えば、Claudeが自分で読み込みます。
- 手動: メッセージの先頭に `/<名前>` と入力します（例: `/meeting-minutes`）。

**確認**:

- `/skills` でSkillの一覧を表示します。
- `/` を入力して、メニューに表示されるか確認します。
- 既存の `skills` フォルダ内での追加・変更は、再起動なしで反映されます。セッション開始時になかった `skills` フォルダを新しく作った場合は `/reload-skills` を実行します。

**Claude Code独自の項目**（他の環境では使えないか、エラーになる場合があります。[11章](#11-複数の環境で使い回すコツ)参照）:

| 項目 | 意味 |
|---|---|
| `disable-model-invocation: true` | Claudeが自動で使わず、`/名前` で呼んだときだけ使う |
| `user-invocable: false` | `/` メニューに出さず、Claudeだけが使う |
| `argument-hint` / `$ARGUMENTS` | `/名前 引数` で渡した値を本文に差し込む |
| `allowed-tools` | Skill実行中、確認なしで使えるツール |
| `context: fork` | 別のサブエージェントで実行する |

### 9.4 OpenAI Codex

**置き場所**（公式ページの検索結果と、Codexのソースコード変更履歴から確認。公式ページ本体は直接閲覧できていません）:

| 範囲 | 場所 |
|---|---|
| 個人 | `$HOME/.agents/skills/<名前>/`（旧来の `~/.codex/skills/` も互換のため読み込まれる） |
| リポジトリ | 作業中のフォルダからリポジトリのルートまで、各階層の `.agents/skills/` |
| 管理者 | `/etc/codex/skills/` |
| システム | Codexに同梱（skill-creator など） |

同じ名前のSkillは統合されず、両方が選択肢に表示されます。

**使い方**:

- 自動: 頼みごとが `description` に合えば使われます。
- 手動: `$<名前>` で指定します（例: `$meeting-minutes で議事録にして`）。

**Codex独自の設定ファイル** `agents/openai.yaml`（任意）:

Skillフォルダ内に `agents/openai.yaml` を置くと、画面での表示名などを設定できます。AIではなくCodexの画面側が読む設定です。

```yaml
interface:
  display_name: "議事録作成"
  short_description: "会議メモから議事録を作成"
  default_prompt: "$meeting-minutes でこの会議メモを議事録にして"
```

他の環境はこのファイルを無視するので、入れておいても害はありません。

**その他**: Skillを追加しても反映されない場合は、Codexを再起動します。
チームや他のリポジトリにSkillを配布したい場合、OpenAIは「プラグイン」としてまとめる方法を案内しています。

### 9.5 GitHub Copilot

**対応している機能**: Copilot cloud agent、Copilot code review、Copilot CLI、GitHub Copilotアプリ、VS CodeとJetBrains IDEのエージェントモード。

**置き場所**:

| 範囲 | 場所 |
|---|---|
| リポジトリ | `.github/skills/`、`.claude/skills/`、`.agents/skills/` のいずれか |
| 個人 | `~/.copilot/skills/` または `~/.agents/skills/` |

**使い方（Copilot CLI）**:

| 操作 | コマンド |
|---|---|
| 一覧 | `/skills list` |
| 詳細（置き場所など） | `/skills info <名前>` |
| 追加後の再読み込み | `/skills reload` |
| 有効・無効の切り替え | `/skills` で選択 |
| 名前を指定して使う | 「`/<名前>` スキルを使って〜」 |

**他の人のSkillを入れる**: GitHub CLI（2.90.0以降）の `gh skill` で検索・確認・インストールできます（パブリックプレビュー）。

```shell
gh skill search 議事録              # 探す
gh skill preview OWNER/REPO SKILL   # インストール前に中身を確認
gh skill install OWNER/REPO SKILL   # インストール
```

GitHubは、Skillは検証されておらず、悪意のある指示やスクリプトを含む可能性があるため、**インストール前に必ず `gh skill preview` で中身を確認する**よう警告しています。

## 10. テストと改善

> この章でわかること: Skillが正しく使われ、期待どおりに動くかを確かめる方法。

### 2種類のテスト

| テスト | 確かめること | やり方 |
|---|---|---|
| 発動テスト | 使うべきときに使われ、使うべきでないときに使われないか | [7章](#7-良いskillの設計手順)で用意した頼み方を、**新しい会話**で1つずつ試す |
| 出力テスト | 使われたとき、期待どおりの成果物が出るか | [7章](#7-良いskillの設計手順)の成功基準と照らし合わせる |

### 発動テストの作り方

| 種類 | 例（議事録Skill） | 期待 |
|---|---|---|
| 明示的な依頼 | 「このメモを議事録にして」 | 使われる |
| 言い換え | 「さっきの打合せ、決まったことを整理しておいて」 | 使われる |
| 状況だけ | 会議の文字起こしを貼って「まとめて」 | 使われる |
| 紛らわしい依頼 | 「議事録をうまく書くコツを教えて」 | 使われない |
| 紛らわしい依頼 | 「この議事録を英訳して」 | 使われない（または翻訳のみ） |

紛らわしい依頼は、明らかに無関係なもの（「天気を教えて」など）ではなく、**キーワードは似ているが目的が違うもの**を選ぶのがコツです。

なお、AIが一人で簡単にこなせる短い依頼では、`description` が合っていてもSkillが使われないことがあります。テストには、ある程度中身のある依頼を使います。

### 改善のサイクル

```
試す → 結果を見る → 原因を考える → 直す → もう一度試す
```

| 症状 | 直す場所 |
|---|---|
| 使われない | `description` に頼み方の言葉や状況を足す |
| 余計な場面で使われる | `description` に対象を絞る言葉を足す（「〜のときは使わない」も可） |
| 使われるが出力が違う | 本文の手順・例・判断のルールを直す |
| 手順の一部を飛ばす | その手順の理由を書き足す、チェックリストにする |

改善のときは、目の前のテスト例だけに合わせた細かい修正を重ねるのではなく、「なぜそうなったか」を考えて一般的な形で直します。
特定の例にだけ効く修正を重ねると、本番の多様な依頼でうまく動かなくなります。

### AIに改善を手伝ってもらう

- **作る係と試す係を分ける**: 1つの会話でSkillを作り（作る係）、別の**新しい会話**でSkillを使ってみる（試す係）。試す係がつまずいた点を、作る係に伝えて直してもらいます。
- **skill-creatorを使う**: Claude.ai、Claude Code、ChatGPT、Codexには、Skill作成を支援するskill-creatorがあります。テストの実施や `description` の改善まで手伝ってくれます。
- **使うモデルごとに試す**: 性能の高いモデルでうまく動いても、軽量なモデルでは説明不足になることがあります。

## 11. 複数の環境で使い回すコツ

> この章でわかること: 1つのSkillを5つの環境で使うための書き方と置き方。

### 原則: 共通部分だけで書く

| 項目 | 方針 |
|---|---|
| `name` | 英小文字・数字・ハイフン。「anthropic」「claude」を含めない。フォルダ名と一致 |
| `description` | 200文字以内。XMLタグを含めない |
| その他の項目 | `license`、`compatibility`、`metadata` だけにとどめる |
| 環境独自の項目 | 必要な環境用のコピーにだけ書く |
| 本文 | 特定製品の機能名（ツール名など）に依存しない書き方にする |

特に注意が必要なのは、**Claude Code独自の項目をClaude.aiにアップロードするとエラーになる**点です（Claude.aiで使える項目は `name`、`description`、`license`、`compatibility`、`metadata`、`allowed-tools` のみ）。

| 独自の拡張 | どこに書くか | 他の環境での扱い |
|---|---|---|
| Claude Code の `disable-model-invocation` など | `SKILL.md` のフロントマター | Claude Codeは未知の項目を無視するが、Claude.aiのアップロードではエラー |
| Codex の表示設定 | 別ファイル `agents/openai.yaml` | 他の環境は無視する |
| `allowed-tools` | `SKILL.md` のフロントマター | 仕様上「実験的」で、書き方も製品ごとに異なる |

### リポジトリでの置き方

開発用リポジトリでチームと共有する場合、各ツールが読む場所は次のとおりです。

| 置き場所 | Claude Code | Codex | Copilot |
|---|---|---|---|
| `.claude/skills/` | 読む | ― | 読む |
| `.agents/skills/` | ― | 読む | 読む |
| `.github/skills/` | ― | ― | 読む |

（「―」は、確認した公式資料に記載がないことを示します。）

3つのツールすべてで使うには、たとえば次のようにします。

```
リポジトリ/
├── .agents/skills/meeting-minutes/   ← 正本（Codex・Copilotが読む）
└── .claude/skills/meeting-minutes/   ← 正本のコピー（Claude Codeが読む）
```

コピーの代わりにシンボリックリンク（別の場所を指す「ショートカット」のような仕組み）を使う方法もありますが、Windowsでは作成に権限が必要な場合があり、ツールごとの扱いも異なります。確実なのはコピーです。コピーする場合は、正本だけを編集し、更新のたびに同期します。

Claude.aiとChatGPTには、同じフォルダをZIPにしてアップロードします。

## 12. スクリプト付きSkill

> この章でわかること: プログラムを同梱するSkillの使いどころと注意点。

### いつスクリプトを使うか

| スクリプトが向く | 文章の指示で十分 |
|---|---|
| 毎回まったく同じ結果が必要な処理（計算、形式チェック） | 判断や文章表現が中心の作業 |
| AIが毎回同じプログラムを書き直している | 一度きりの処理 |
| 間違えると困る処理（ファイルの一括変更など） | やり方が状況で変わる作業 |

スクリプトは中身を読まずに実行できるため、AIの作業メモを消費しません。結果だけが返ります。

### 書き方のポイント

- 本文で、**実行するのか、読んで参考にするのか**をはっきり書きます。
  - 実行: 「`scripts/check.py` を実行して形式を確認する」
  - 参考: 「計算方法は `scripts/calc.py` を参照する」
- 必要なソフトやライブラリを本文に明記します。
  - Claude.aiとClaude Codeは、PyPIやnpmなどからパッケージを取得できます。Claude APIでは実行中に追加インストールできません。
- スクリプト内でエラーを処理し、わかりやすいメッセージを出すようにします。
- 数値の設定値には、なぜその値なのかをコメントで書きます。

### プログラミングが専門でない人へ

スクリプトはAIに書いてもらって構いません。ただし、次の点を必ず確認します。

1. 「このスクリプトは何をするか」「どのファイルを読み書きするか」「ネットに接続するか」をAIに説明させる
2. テスト用のファイルで実行し、結果を確認する
3. 意味のわからない処理が残っていたら、使わない

### 実行の許可について

`allowed-tools` で `shell` や `bash`（コマンドを実行するツール）を事前に許可すると、確認なしでコマンドが実行されるようになります。
GitHubは、Skillとスクリプトを確認し、作成元を完全に信頼できる場合を除いて、`shell` や `bash` を事前許可しないよう警告しています。

## 13. 安全に使うために

> この章でわかること: Skillを作る・入れるときのリスクと対策。

### 他人が作ったSkillを入れるとき

Skillは「AIへの指示」と「実行されるプログラム」の組み合わせです。悪意のあるSkillは、次のような被害を起こし得ます。

- 隠れた指示で、AIに意図しない動作をさせる（プロンプトインジェクション）
- 同梱のスクリプトで、ファイルを外部へ送信する・削除する

対策:

- **入れる前に、`SKILL.md` とすべての付属ファイルを読む**（読めない場合は、AIに「危険な処理がないか」を説明させる）
- 出所が信頼できるものだけを使う（公式リポジトリ、社内で管理されたものなど）
- 会社で使う場合は、社内のルール（使ってよいツール、データの扱い）に従う

各サービスにも安全の仕組みがあります。ChatGPTはアップロードされたSkillを検査し、Claude.aiのTeam / Enterpriseでは組織のセキュリティスキャンや公開前レビューを設定できます。

### 自分でSkillを作るとき

- **パスワードやAPIキーなどの秘密情報を書かない**。Skillは共有されることがあり、AIの作業メモにも読み込まれます。
- **社外秘の情報を書く場合は、共有範囲を確認する**。
- 外部サービスと連携する場合は、Skillに認証情報を書くのではなく、各サービスの正式な接続機能（MCPやコネクタ）を使います。

### 更新と版管理

- `metadata` に版数を書いておくと、どの版を使っているかがわかります（例: `version: "1.1"`）。
- 変更したら、[10章](#10-テストと改善)のテストをもう一度行います。
- Claude.aiで共有したSkillは、更新すると受け取った人も次回から新しい版を使います。影響が大きい変更は事前に知らせます。
- 開発用リポジトリに置く場合は、Gitで変更履歴を管理できます。

## 14. よくある失敗と対処

| 症状 | よくある原因 | 対処 |
|---|---|---|
| Skillが一覧に出ない | ファイル名が `SKILL.md` でない（`skill.md.txt` など） | 拡張子を表示して確認し、`SKILL.md` に直す |
| 〃 | 置き場所の階層が違う（`skills/SKILL.md` に直接置いた等） | `skills/<名前>/SKILL.md` の形にする |
| 〃 | ZIPの中身の構造が違う | フォルダ自体を圧縮し直す |
| 〃 | フロントマターの書式エラー | 1行目が `---` か、`name:` の後に半角スペースがあるか確認 |
| アップロードでエラー | `name` の文字種違反（大文字、日本語、空白） | 英小文字・数字・ハイフンにする |
| 〃 | 使えない項目がある（Claude.ai） | 共通の項目だけにする |
| 〃 | `description` が長すぎる | 200文字以内にする |
| 使われない | `description` に頼み方の言葉がない | 実際の言い方を足す |
| 〃 | Skillがオフ | 一覧でオンにする |
| 〃 | 依頼が簡単すぎる | ある程度中身のある依頼で試す。名前を指定して頼む |
| 余計な場面で使われる | `description` が広すぎる | 対象を絞る。「〜には使わない」と書く |
| 手順を飛ばす・書式が崩れる | 本文が長すぎる、理由がない | 詳細を `references/` に分ける。理由を書く |
| 付属ファイルが読まれない | 本文からのリンクがない、階層が深い | `SKILL.md` から直接リンクする |
| Windowsで作ったSkillが他で動かない | パスに `\` を使っている | `/` に統一する |

## 15. 作成チェックリスト

### 形式

- [ ] ファイル名は `SKILL.md`（大文字）
- [ ] 1行目が `---` で始まり、フロントマターが `---` で閉じている
- [ ] `name` は英小文字・数字・ハイフンのみで、フォルダ名と一致している
- [ ] `name` に「anthropic」「claude」を含まない
- [ ] `description` は200文字以内で、XMLタグを含まない
- [ ] 使い回す場合、環境独自の項目を共通版に入れていない

### 内容

- [ ] `description` に「何をするか」と「いつ使うか」の両方がある
- [ ] `description` に利用者が実際に使う言葉が入っている
- [ ] 本文は500行以内で、詳細は `references/` に分けている
- [ ] 付属ファイルは `SKILL.md` から直接リンクしている
- [ ] 重要なルールには理由が書いてある
- [ ] 入力と出力の具体例がある
- [ ] 用語が統一されている
- [ ] 時期で変わる情報を書いていない
- [ ] パスの区切りは `/`

### テスト

- [ ] 使われるべき頼み方を3つ以上、新しい会話で試した
- [ ] 使われるべきでない紛らわしい頼み方で試した
- [ ] 出力が成功基準を満たしている
- [ ] 使う予定のすべての環境・モデルで試した

### 安全

- [ ] パスワードやAPIキーなどの秘密情報を含まない
- [ ] スクリプトの動作を理解している（または説明を受けて確認した）
- [ ] 共有範囲が適切である

## 付録B テンプレート

書き込み式のテンプレートを用意しています: [skill-guide/templates/my-skill/SKILL.md](skill-guide/templates/my-skill/SKILL.md)

```markdown
---
name: my-skill
description: （何をするSkillか）を行う。（どんな頼み方・状況のときに使うか）ときに使う。
---

# （Skillの名前）

## 目的
（何を達成したいか。完成物を受け取る人と用途）

## 手順
1. （最初にやること）
2. （次にやること）
3. （出力の形式）

## 判断のルール
- （迷いやすい場面での決め方と、その理由）

## 例
入力: （典型的な入力）
出力: （期待する出力）
```

使い方:

1. `my-skill` フォルダをコピーし、フォルダ名と `name` を同じ名前に変えます。
2. `description` と本文を書き換えます。
3. [10章](#10-テストと改善)の方法でテストします。

## 付録C 作例の解説

5つの環境すべてで使えるように書いた作例です: [skill-guide/examples/meeting-minutes/](skill-guide/examples/meeting-minutes/)

```
meeting-minutes/
├── SKILL.md              ← 手順・判断のルール・例
└── references/
    └── format.md         ← 議事録の書式（必要なときだけ読まれる）
```

この作例で使っている工夫です。

| 工夫 | 該当箇所 | ねらい |
|---|---|---|
| 頼み方を複数書く | `description` の「議事録にして」「会議メモをまとめて」「打合せ記録を作って」 | 言い換えにも反応させる |
| 状況も書く | `description` の「文字起こしが貼り付けられたとき」 | 明示的に頼まれなくても使わせる |
| 理由を書く | 「推測で埋めない」の後の「後から証拠として読まれるため」 | 想定外の場面でも正しく判断させる |
| 不明時の扱いを決める | 「要確認」と書く | 情報の捏造を防ぐ |
| 書式を分ける | `references/format.md` | 本文を短く保つ |
| 例を入れる | 入力と出力の抜粋 | 説明文だけより正確に伝える |
| 共通の項目だけ使う | フロントマターは `name` と `description` のみ | どの環境でもそのまま使える |

動作確認（2026-10-17、Claude Code 2.1.302）:

- 「さっきの打合せのメモです。整理しておいて。」＋会議メモ → Skillが使われ、`references/format.md` の書式で出力された（「議事録」という言葉がなくても発動）
- 「議事録をうまく書くコツを3つ、短く教えて。」 → Skillは使われず、通常の回答になった
- Claude.ai / ChatGPT / Codex / Copilot での動作は未確認

各環境での置き方:

| 環境 | 置き方 |

| Claude.ai / ChatGPT | `meeting-minutes` フォルダをZIPにしてアップロード |
| Claude Code | `~/.claude/skills/meeting-minutes/` または `.claude/skills/meeting-minutes/` にコピー |
| Codex | `~/.agents/skills/meeting-minutes/` または `.agents/skills/meeting-minutes/` にコピー |
| Copilot | `~/.copilot/skills/meeting-minutes/` または `.github/skills/meeting-minutes/` にコピー |
